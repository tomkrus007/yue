# 本地存储与索引

## 1. 存储分层

```
CoremailEngine
├── Database            (45 符号)   → sqlite3mc 封装（元数据/账号/设置/缓存）
├── MailStorage         (41 符号)   → 邮件原始文件与元数据落盘
├── MailStorageEncode  (196 符号)   → 邮件文件级加密/编码（SM4 / AES）
│   ├── MailStorageKeyManagerImp    (5 符号)
│   ├── PaddingEncryptEncode<T>
│   ├── Sms4PaddingEncrypt
│   └── AesPaddingEncrypt
├── MailIndex          (139 符号)   → Xapian 全文索引
├── MailIndexBuilder    (15 符号)   → 索引构建
└── MailIndexMisc       (1 符号)
```

三层职责清晰：**关系型元数据（SQLite）** + **邮件原文（加密文件）** + **检索索引（Xapian）**。

## 2. SQLite：加密的 sqlite3mc

### 2.1 事实

二进制链接的是 **sqlite3mc**（`sqlite-multiple-ciphers`）分支，不是原生 SQLite，也不是单算法 SQLCipher。证据：

```
cmclient_sqlite3mc_version
cmclient_sqlite3mc_config
cmclient_sqlite3mc_config_cipher: cipher name ('%s') or parameter ('%s') missing
cmclient_sqlite3mc_config_cipher: codec parameter table not found
cmclient_sqlite3mc_config_cipher: global change of parameter '%s' for cipher '%s' not supported
cmclient_sqlite3mc_config_cipher: SQLCipher legacy version %d out of range [%d..%d]
cmclient_sqlite3mc_cipher_salt
cmclient_sqlite3mc_codec_data
```

支持的算法至少包括：**AES（CBC/CTR）、ChaCha20、ChaCha20-Poly1305**（`chacha20_poly1305_cipher`、`ECDHE-*-CHACHA20-POLY1305` 是 OpenSSL 侧，但 sqlite3mc 的 `chacha20` codec 独立存在）。

### 2.2 自研加密扩展

`CoremailEngine::Database` 有一组关键方法：

```cpp
Database::_registerCustomEncryptMethod(...)
Database::_setkey(...)
Database::_rekey(...)
Database::setDefaultEncMethodByExtName(...)
Database::upgradeEnc(...)
Database::DecodeEncDB(...)
Database::detectDBExtName(...)
Database::getExtName()
Database::getPlainExtName()
Database::rebuildDB(...)
Database::repareDB(...)
```

**推断**：Coremail 在 sqlite3mc 上注册了**自己的 codec**（很可能是 SM4），并通过**文件扩展名**区分加密级别：

| 扩展名 | 含义（推断） |
|---|---|
| `account.dat` | 明文/兼容格式 |
| `account.edat` | 加密（encrypted） |
| `account.sdat` | 安全加密（secure / 强加密） |

`Setting::EncFileExt`、`Setting::loadFromFile` / `loadObjFromFile` / `loadObjsFromFile` 说明**设置文件本身也是加密落盘的**，且按扩展名选择编解码器。

另有两个数据文件族：`d.dat`、`v.dat`、`m_buf.dat`、`m_fmt.dat`——**推断**是索引/搜索的中间产物（`m_` 前缀可能是 mail）。

### 2.3 明文形态的证据

`getPlainExtName()` / `getEncExtName()` 成对出现，且 `upgradeEnc` 存在，说明支持**从明文库升级为加密库**（老用户升级场景）。`_registerCustomEncryptMethod` 允许运行时注册，**推断**是为了兼容不同产品线的算法（国密版 vs 国际版）。

## 3. 邮件原文存储

### 3.1 文件级加密

`MailStorageEncode` 是 196 个符号的子系统，核心模板：

```cpp
template<class Enc> class PaddingEncryptEncode;
MailStorageEncode::Sms4PaddingEncrypt;   // SM4 分组填充加密
MailStorageEncode::AesPaddingEncrypt;    // AES 分组填充加密
```

构造函数都是 `(std::string const&)`——即**一个密钥/口令字符串**。与 `MailStorageKeyManagerImp`、`MailFile::check_header(path, keyManager, ...)`、`MailFile::open_to_read(unique_ptr<FileSystemBase>&&, path, keyManager, ...)` 配合。

### 3.1.1 文件头格式（反编译确认）

`MailFile::check_header`（`0x101915a34`，证据 `ev_a11b7901075307e3cc4d982ad81189793d84780f1c32d183d6748c137e7eb45c`）的实测逻辑：

```cpp
loop_read(stream, &header, 0x40);                 // 固定读 64 字节
if (read != 0x40)        → "File %v read header fail"
if ((uint)header != 0x736d6d63) → "File %v Prefix mismatch: %v"
if (header.version != 1) → "File %v Version mismatch: %v"
findKey(header[0x20]);                            // 失败 → "Key mismatch in history"
build_encoder(header[0x24] /*compress*/, flag, header[0x08] /*encode*/, key);
```

| 偏移 | 含义 | 证据强度 |
|---|---|---|
| `0x00` | magic **`"cmms"`**（Coremail Mail Storage，小端 `0x736d6d63`） | 强 |
| `0x04` | version，**必须为 1** | 强 |
| `0x08` | `EncodeType`（决定用 SM4 还是 AES 还是明文） | 中 |
| `0x10` / `0x18` | 两个 8 字节字段（`0x18` 经过字节反转） | 中 |
| `0x20` | **`keyId`（uint32）** | 强 |
| `0x24` | `CompressType`（zstd / 无压缩） | 中 |
| `0x28` | 一个 uint32 | 弱 |

**由此产生的两个结论**：

1. **邮件文件是自描述容器**，不是 RFC822 原文——即使拿到文件也需要 key 才能读；
2. **支持密钥轮换**：`keyId` 由 `MailStorageKeyManagerImp::findKey(keyId, out)` 在 `std::map<uint32, string>` 里查找（树节点 `+0x20` = keyId、`+0x28` = key）。旧文件保留旧 keyId，改密码后新文件用新 keyId，**无需全量重加密**。

**修正第一版的推断**：头里"标识算法与版本"是对的，但还额外标识了 **keyId** 与 **compressType**——第一版漏掉了这两个关键字段（也是"为什么改密码后旧邮件还能读"的答案）。

### 3.1.2 SQLite 数据库加密（反编译确认）

第一版只知道"sqlite3mc + 自研 codec"，算法完全未知。反编译四个函数后可以给出确定结论：

| 函数 | 地址 | 行为 |
|---|---|---|
| `Database::openImp` | `0x10197ebb8` | `sqlite3_open16(path)` → `initEncMethod(name, db)` → `sqlite3_key(db, key, len)` → 注册 `busy_handler` |
| `Database::_setkey` | `0x101980da8` | `initEncMethod(...)` → `sqlite3_rekey(db, key, len)`；失败则 `PRAGMA page_size=4096` + `VACUUM` + 再次 `rekey` |
| `Database::_rekey` | `0x101980ae4` | 与 `_setkey` 同构（换钥路径） |
| `Database::initEncMethod` | `0x1019810cc` | **按文件扩展名选 cipher** |
| `Database::_registerCustomEncryptMethod` | `0x1019813fc` | `sqlite3mc_register_cipher(...)` + `Sqlite3Env::addEncMethod(ext, cipher, bool)` |

#### cipher 选择规则（`initEncMethod`，证据 `ev_dc8b94a24ae371ed1c8bd9269fbfa729f97effd952d2a13c03fa62e849106604`）

```cpp
// 从 wstring 文件名反向扫描 '.' 取扩展名
ext = extension_of(name)
if (ext == L".edb") {
    idx = sqlite3mc_cipher_index("chacha20");
    sqlite3mc_config(db, "cipher", idx);
} else {
    // 查全局表 (anonymous namespace)::env: ext -> cipher name
    for (entry : env)
        if (ext == entry.ext) { sqlite3mc_config(db, "cipher", sqlite3mc_cipher_index(entry.cipher)); break; }
}
```

**结论**：

1. **`.edb` 数据库使用 ChaCha20**（sqlite3mc 内置的 `chacha20` cipher），这是确定的，不再是推断。
2. 其他扩展名（`.edbx2`、`.sdat` 等）走 `Sqlite3Env` 的"扩展名 → cipher 名"注册表，可由 `_registerCustomEncryptMethod` 在运行时扩展（`addEncMethod` 就是往这张表插入）。
3. 加密开关是**按文件扩展名**而不是按配置项——这与 `getPlainExtName()` / `getEncExtName()`（全局 wstring，`DAT_104da6678`）配合，即"同名数据库的明文/加密两态由扩展名区分"。
4. 换钥流程是 sqlite3mc 的标准做法（`rekey` → `PRAGMA page_size=4096` → `VACUUM` → 再 `rekey`），说明**改密码会重写整个库**。
5. `Database` 对象布局：`+0x10` = `std::wstring` 加密方式名，`+0x28` = `sqlite3*`，`+0x30` = 最近一次 `sqlite3_exec` 错误码。

**仍未还原**：`Sqlite3Env` 表里"自定义扩展名 → 自定义 cipher"的具体条目，以及 `_registerCustomEncryptMethod` 的两个函数指针（`param_1`/`param_2`）指向哪个 codec 实现。`.edb → chacha20` 是唯一能从代码里直接读出的映射。

### 3.2 读写路径

```cpp
MailStorage::_toSave(bool, int, unsigned long long, EncodeType, unsigned int,
                     wstring const&, unsigned long, ...)
MailStorage::_toLoad(int, std::string const&, bool)
MailStorage::_moveFile(std::string const&, int, bool, int, int*)
MailStorage::_initMailStorage(vector<wstring> const&, unsigned long)
MailStorage::_initArchiveMailStoragePath(vector<wstring> const&, unsigned long)
```

关键点：
- **`EncodeType` 是显式参数**，说明同一存储层同时支持明文与加密（导入邮件可能先明文落地再加密，或反之）。
- **`_initArchiveMailStoragePath` 独立于 `_initMailStorage`**：归档邮件有**单独的存储根路径**，与在线邮箱分开管理。这与 `LANG_ARCHIVE_FOLDER_PREFIX`、`archiveMails`/`autoArchiveMails`/`archiveSchedules` 对应。
- `_moveFile(..., int*, ...)` 带 `int*` 出参——**大概率是错误码或新索引**。

#### 3.2.1 `EncodeType` 的实际取值（反编译确认）

`MailFile::build_encoder(CompressType, level, EncodeType, key)`（`0x101914574`，证据 `ev_636af176e361709146c295eb43e9a37972d5a4055d1f3a387d73f5ec83cf6adb`）：

| 层 | 取值 | 实现 |
|---|---|---|
| CompressType | 0 / 1 / 2 | 不压缩 / `CompressFileEncodeStream_Zlib` / `CompressFileEncodeStream_ZStd` |
| EncodeType | 0 | `PlainEncode`（明文） |
| EncodeType | 1 | `XorEncode`（流式异或） |
| EncodeType | 2 | **`PaddingEncryptEncode<AesPaddingEncrypt>`**（OpenSSL AES） |
| EncodeType | 3 | **`SM4PaddingEncrypt`**（GmSSL `sm4_setkey_enc/dec`） |
| EncodeType | 4 | `FastXorPaddingEncrypt`（16 字节滚动异或密钥） |
| EncodeType | 5..15 | `Injection` 外挂 `ExternalPaddingEncryptEncode`（第三方/定制 codec 插件位） |

三种加密 codec 的密钥派生细节：

- **AES**（`Encode::AES::setKey`，`0x100f00f18`）：密钥 16/24/32 字节 → AES-128/192/256，模式只认 `ecb`（无 IV、关闭 PKCS 填充）或 `gcm`（带 IV）。见 `05` 4.1。
- **SM4**（`0x1019220b8`，证据 `ev_d7ba668556d200ecf0e1f01079e0de98afe150471d7058b12548fa8404338972`）：密钥串直接 `memcpy` 后喂给 GmSSL 的 `sm4_setkey_enc` / `sm4_setkey_dec`，**无 KDF**。
- **FastXor**（`0x10191ba44`，证据 `ev_c4d740238396f7c1e80ec0ba55d795613fd91739e9af655a39af3cf4f460a0eb`）：派生 16 字节密钥 `k[i] = (i < len ? key[i] : 0x1c) ^ 0x1c`，是**混淆级**而非强加密。

可见 `EncodeType` 是"每账号/每存储区可选"的档位：0 明文、1 弱异或、2 AES、3 SM4、4 快速异或、5..15 插件。信创版本大概率用 3，标准版用 2。

#### 3.2.2 默认档位是 4（FastXor）——一个意外发现

`MailEngine::_initEnginePackeType`（`0x100ffdfbc`，证据 `ev_d684cff211e3d2b5c80579d8fda09c8bc77c01c211c77040ceaa235418f3bab1`）是 `MailStorage::setEncodeType` 的**唯一调用者**：

```cpp
key = MailStorage::getEncodeKey();      // 当前密钥串
MailStorage::setEncodeType(mailStorage, 4, key);   // ← 固定传 4
*(uint*)(mailStorage + 0xc4) = 3;       // 压缩档位
*(uint*)(mailStorage + 0xc8) = 4;       // EncodeType 再存一份
```

即**引擎初始化的默认档位是 4 = FastXorPaddingEncrypt（滚动异或混淆），不是 AES/SM4**。`setEncodeType(type, key)` 本身只是 `this+0xb8 = type` + `addKey(key, true)`（设当前密钥）。

这说明 AES(2)/SM4(3) 档位**不在默认路径上**，需要由别的配置/版本分支切换（未定位到切换点）。对逆向的直接影响是：**默认安装下的邮件正文保护强度只有混淆级**，但 `cmms` 头里的 `EncodeType` 字段仍能正确指示实际档位。

#### 3.2.2 keyId 的生成方式（反编译确认）

`MailStorageKeyManagerImp::addKey`（`0x10190b1e8`，证据 `ev_7fc71c1a8ce3356e15eaefd81c7f504c3ac4724e2369bf226a65337b8b10d7d3`）：

```cpp
keyId = TextProcess::cmx_string_hash_value(keyString);  // 32 位哈希，不是随机数
```

`findKey(keyId, out)` 在一棵 `std::map<uint32, std::string>` 里按 keyId 查回密钥；`MailStorage::addKeyHistory(list<string>)`（`0x10190b54c`）把整份"密钥历史"逐条 `addKey(key, false)` 灌进去。这就是 `check_header` 报 `Key mismatch in history` 的由来。**密钥串本身的来源**（口令原文 / KDF 结果 / 服务端下发）尚未定位。

### 3.3 导入路径

- `ImportPSTFile` + `pstsdk`（436 符号）：PST 的目录结构、属性表、流对象都被静态链入。
- EML/MSG：`Info.plist` 声明了 `com.apple.mail.email`、`com.apple.mail.emlx`、`*.eml`、`*.msg`，属文档打开即导入。
- `rtf2html`：处理 Outlook 的 TNEF/RTF 正文。

## 4. Xapian 全文索引

### 4.1 后端与文件

同时存在 **Glass**（现代）与 **Chert**（旧版）两套符号：

```
GlassWritableDatabase, ChertWritableDatabase
GlassDatabase, RemoteDatabase
Failed to open chert version file for reading
Failed to create chert version file:
N6Xapian20DatabaseVersionErrorE
N6Xapian9CompactorE
```

**推断**：Chert 符号来自 Xapian 库本身（为兼容旧库版本保留），实际使用的是 **Glass**。`Xapian Glass` 字符串直接出现。

Glass 后端的标准文件族全部出现在二进制里：

```
postlist.DB  postlist.baseA  postlist.baseB  postlist.glass
termlist.DB  termlist.baseA  termlist.baseB  termlist.glass
record.DB    record.baseA    record.baseB    record.glass
position.DB  position.baseA  position.baseB  position.glass
spelling.DB  spelling.baseA  spelling.baseB  spelling.glass
synonym.DB   synonym.baseA   synonym.baseB   synonym.glass
```

`baseA` / `baseB` 是 Xapian 1.4 Glass 的**双份 B-tree 根页**（原子提交用），这进一步确证版本为 1.4.x。

### 4.2 中文分词

`dict/` 目录：

| 文件 | 大小 | 用途 |
|---|---|---|
| `jieba.dict.utf8` | 5.07 MB | cppjieba 主词典 |
| `jieba.dict.utf8.lite` | 1.55 MB | 精简词典 |
| `hmm_model.utf8` | 519 KB | HMM 新词发现模型 |
| `idf.utf8` | **0 字节** | 空文件（IDF 未启用/未随包） |
| `stop_words.utf8` | 8.9 KB | 停用词 |
| `user.dict.utf8` | 49 字节 | 用户词典（几乎为空） |
| `stcharacters.txt` | 34 KB | 单字表 |

**观察**：`idf.utf8` 为 0 字节，说明 **TF-IDF 关键词抽取能力实际未启用**（或运行时另有来源）。`user.dict.utf8` 只有 49 字节，说明用户自定义词典是预留位。

### 4.3 索引维护

```cpp
MailIndex::compact(set<uint64_t>&, set<string>&, bool&)
MailIndexBuilder
ForceUpgradeSearchIndexType          // 强制升级索引类型（Chert→Glass？）
LANG_MSG_INFO_SEARCH_INDEX_NEEDUPGRADE_MSG / _TEMPLATE / _TIP
```

`ForceUpgradeSearchIndexType` 与对应的三条 UI 文案说明：**旧版本的索引格式会在升级时被强制重建**，并提示用户。这是 `LANG_*SEARCH_INDEX_NEEDUPGRADE*` 的来源。

`MailIndex::compact` 的签名（两个 `set` 出参 + `bool&`）暗示压缩时会返回"被清理的 UID 集合"和"被清理的 term 集合"。

## 5. 归档（Archive）

归档是本客户端一个独立子系统，不是简单"移动文件夹"：

| 证据 | 含义 |
|---|---|
| `_initArchiveMailStoragePath` | 独立存储根 |
| `LANG_ARCHIVE_FOLDER_PREFIX` | 归档文件按前缀命名 |
| `archiveMails` / `archiveMailsDetect` / `autoArchiveMails` | 手动 + 自动归档 |
| `LANG_ARCHIVE_PROGRESS_DLG_TITLE/TIP` | 有进度对话框（说明是长任务） |
| `LANG_ARCHIVE_DISK_SPACE_FULLED` | 磁盘满处理 |
| `LANG_ARCHIVE_STRID_ARCHIVEMAIL_INFOTIP` | `STRID` 前缀 → 服务端"归档任务 ID"概念 |
| `archiveExpiredSchedules` | 日程也会归档 |
| `LANG_BATCH_ARCHIVE_SELECT_EARLIER` / `START_END_DATE_TIP` | 支持按日期区间批量归档 |

**推断**：归档把邮件从"在线邮箱索引"搬到"归档索引"，可能是**服务端主导、客户端落本地副本**的双轨模式（`STRID` = server task id）。
