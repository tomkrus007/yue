### 1.3 配置防篡改

```
LANG_SECURITY_SETTING_INVALID=安全配置文件已被篡改。
```

结合 `privatization-setting.js` 里的 `hash` 字段，**推断**启动时会：
1. 读文件内容（去掉 `hash` 字段后）；
2. 计算 SHA-256；
3. 与 `hash` 比较；不等则报警并**回退到内置默认值**（防止用户改配置解锁被禁用的功能，比如打开被企业禁用的 AI）。

## 2. 版本检查与升级

### 2.1 服务端接口

```
/coremailclient/clientVersionCheck.jsp
```

**第二版补充（反编译）**：

- `UpgradeContext::checkVersion()`（`0x101558d00`）里**还硬编码了另一条升级检查地址**：

  ```
  https://pcmail.coremail.cn/lunkr/s/json?func=cim.common:checkVersion
  ```

  即升级检查同时走"客户侧 Lunkr SaaS 端点"和"自有服务端 JSP"两条路。
- 该函数体内**未见任何签名/哈希校验**（无 `EVP_*`、无 `SM2_*`、无摘要比较），只有 HTTP 请求 + JSON 解析。
- `Protocol::upgradeApp(...)`（`0x1015587b8`，即 `/coremailclient/clientVersionCheck.jsp` 的唯一 xref）只负责组装 `Event_UpgradeApp` 请求，同样**没有验签逻辑**。

### 2.2 日志格式（可还原判定逻辑）

```
checkversion localversion:%v, upgrade.check(v:%v), upgrade.xxx.%v(%v)
```

**推断**：`upgrade.xxx.VERSION(RESULT)` 是逐版本判定的输出——即客户端会**逐个检查中间版本的升级脚本**（数据库 schema 迁移），而不是直接跳到最新版。这是"**顺序升级链**"的证据。

### 2.3 升级相关的类与开关

| 符号/字符串 | 含义 |
|---|---|
| `UpgradeCoremailDlg` | 升级对话框（暴露出 `OnBtnUpgrade`） |
| `HandleUpgradeCoremailEvent` / `Event_UpgradeApp` | 升级事件 |
| `HandleUpgradeCoremailPath` | 升级包路径处理 |
| `disable_auto_upgrade` | 禁用自动升级（运维开关） |
| `disable_manual_upgrade` | 禁用手动升级（**强制锁定版本**，企业场景） |
| `mini_upgrade` | 静默/增量升级 |
| `reportDownloadUpgrade` / `reportDownloadUpgrade` | 升级下载上报 |
| `exec upgrade SN table in db` | **数据库 schema 版本表**（`SN` = serial number） |
| `/coremail_plugin/config/client_expirydate.ini` | 客户端过期日期（**强制到期**机制） |
| `not needupgradetoenc` | "不需要升级为加密（库）" |

**关键推断**：

- `client_expirydate.ini` 说明存在**客户端有效期**机制——过期后可能限制登录（便于企业强制换版）；
- `Exec upgrade SN table in db` + `Database::upgradeEnc` 说明升级会**同时迁移数据**（schema + 加密格式）；
- `disable_manual_upgrade` 让管理员可以**完全禁止用户手动升级**，只能由服务端下发。

### 2.4 升级包形态

未发现 `.dmg` 下载或 `sparkle` 相关字符串，**推断**升级是"**下载安装包 → 调起安装**"（`LANG_CHECKUPGRADE_DOWNLOADOK` / `_SETUP` / `_UPGRADE` 三条文案对应下载完成→安装→升级三个阶段）。

## 3. 崩溃上报（CrashRpt）

`licensing/CrashRpt/` 下只有 `Authors.txt`、`License.txt`（这是开源库 CrashRpt 的许可文件）。二进制中：

```
crashfile del fail / succ
crashinfo load error / not found / parse error
crashreport_rcptemail        // 崩溃报告的收件邮箱
report_enable / report_count / report_log_count / report_collect_time
report_svr / report_url
reportdata empty, bCrash(%d)
reportdata empty, type(%v), host(%v)
```

**观察**：**CrashRpt 是 Windows 库**（DumpUpload 等），但它出现在 macOS 包里。结合 `reportdata empty, type(%v), host(%v)` 的结构，**推断**：

- 实际的崩溃收集是**自研实现**（`crashfile`/`crashinfo` 的读写），CrashRpt 只保留了许可文件（或复用了其 dump 格式）；
- 上报目标是 `report_svr`/`report_url`（`privatization-setting.js` 里 `report_url: "DEFAULT"` 表示用内置默认地址）；
- `crashreport_rcptemail` 说明**崩溃报告可能以邮件形式发送**（讽刺但合理——这是个邮件客户端）。

### 3.1 埋点上报复用同一通道

`LA.uploadData` → `callPC("uploadTrackData")` → 原生侧，而原生侧的 `report_*` 配置项与崩溃上报共用。**推断**：**埋点与崩溃上报走同一套上报通道/服务**。

## 4. 埋点系统（LA）

`template/lib/la/la.js`（1,980 字节）是一个**极简自研埋点库**，完整逻辑如下：

```js
class LaCache {           // localStorage 缓存
  get() / set() / remove()
}

function LA({ uid, email, eventPrefix, dt = 5, uploadCycle = 5, intervelCycle = 10 }) {
  const cacheKey = `LA_${uid||email||""}_cache`;

  track(event, opts) {
    // 1. 加前缀
    // 2. t = 当前秒级时间戳
    // 3. 基础结构 {t, op:"1", val:1}
    // 4. 若 opt.log 存在则合并
    // 5. 若缓存里已有同名事件，且距上次 <= dt(5秒) → 累加 val
    //    否则 → unshift 新记录
    // 6. 不立即上报，写入 localStorage
  }

  trackDuration(event, startTime, opts) {
    // op:"2"，val = 耗时（秒，或 ms 取决于 opts.unit）
  }

  uploadData() {
    // 把缓存摊平成 [{e:事件名, logs:[...]}]，调 callPC("uploadTrackData")
    // 然后清空缓存
  }
}
```

### 4.1 语义分析

| 字段 | 含义 |
|---|---|
| `op: "1"` | **计数**事件（累加 `val`） |
| `op: "2"` | **耗时**事件（`val` = 秒或 ms） |
| `op: "3"` | **数值**事件（如 token 用量，见 `coremail/08`） |
| `dt: 5` | **聚合窗口**：5 秒内同名事件合并为一条（`val` 累加） |
| `uploadCycle` / `intervelCycle` | 定时上传周期（5 / 10） |

**这是一个"客户端聚合 + 批量上报"的设计**：避免高频事件（滚动、按键）直接打服务端。

### 4.2 已知埋点事件

从各处的 `la.track(...)` 调用可收集到：

| 事件 | op | 说明 |
|---|---|---|
| `<trigger>/token-AI_<feature>` | 3 | AI token 用量（translate/summary/compose…） |
| `uploadTrackData` 里的 `e` 字段 | — | 事件名由调用方决定 |
| `startCompose` | — | 写信开始（`Plugin_Monitor::onStartCompose`） |

**推断**：埋点事件名是**业务侧约定**的字符串（如 `translate/token-AI_translate`），原生侧只做透传，不做枚举校验。

### 4.3 `LA.emptyInstance` / `LA.uploadData` 静态方法

```js
LA.emptyInstance = { track: () => {}, trackDuration: () => {} };
```

提供**空实现单例**，用于"埋点被禁用"的场景（避免到处写 `if (la)`）。这是常见的降级设计。

`LA.uploadData({uid, dt})` 静态方法则用于**冷启动时补传**上次未上报的缓存（从 localStorage 读出直接调 `getTrackingData`）。

### 4.4 隐私要点

- 缓存 key 含 uid/email，**多账号数据分开**；
- `history_record_rcpt: false`（`address-setting.js`）说明**不记录普通收件人**；
- 但 AI 的 token 用量上报包含业务上下文（feature 名）；
- 埋点通过 `uid` 可关联到具体用户 → **属于可识别个人的遥测**，不是聚合匿名统计。
