# 邮件引擎与协议栈

## 1. 引擎核心：`CoremailEngine::MailEngine`

`MailEngine` 在符号表中出现 **17,492** 次，是整个二进制的绝对中心。它既是"账号级引擎实例"（一个账号一个实例，`shared_ptr<MailEngine>` 在多处作为第一个参数出现），也是协议调度的持有者。

典型签名（反混淆后的可读形式）：

```cpp
Protocol::reloadCoremailAIHubSettings(shared_ptr<MailEngine>, function<void()>,
                                      function<void(Login_RetCode, ara::var)>)
```

可以看到引擎方法是**异步回调式**的：`(错误码, ara::var 响应)` 双参回调是全局约定。

### 1.1 ara 库

`ara` 是自研基础库（1.1k 符号），提供：
- `ara::var`：动态类型（类似 JSON value），贯穿全部协议边界；
- `ara::http`：异步 HTTP 客户端与服务端（`async_server_request` / `async_respond`）；
- `ara::singleton<T>`：全局单例（如 `AIMCPSetting`）；
- 日志与文件系统工具。

`ara::http` 同时被用来实现 HTTP 客户端和**本地 HTTP 服务**，所以 `Plugin_CommandServer_Http` 才能复用同一套栈。

## 2. 四套协议实现

| 协议 | 上下文类 | 客户端类 | 符号量级 |
|---|---|---|---|
| Coremail 私有协议 | `ProtocolContext_Coremail` | `CoremailClient` | 4,317 / 1,435 |
| IMAP | `ProtocolContext_Imap` | `ImapClient` | 1,310 / 1,600 |
| POP3 | `ProtocolContext_Pop3` | `Pop3Client` | 1,201 / 1,453 |
| EWS (Exchange) | `ProtocolContext_EWS` | —（用 SOAP over HTTP） | 1,054 |
| EWS 推送 | — | `EWSPushmailClient` | 149 |

**私有协议是首选**：`ProtocolContext_Coremail` 的符号量是 IMAP 的 3.3 倍，说明绝大多数功能（尤其是标签、日程、共享文件夹、撤回、归档）只在私有协议上完整实现，IMAP/POP3/EWS 是"兼容降级"路径。

配置中心也印证了这一点：

```json
// app/conf/privatization-setting.js
"supported_protocol": "proprietary,imap,pop3,ews"
```

顺序即优先级。

## 3. 推送与实时通道

三条并存的推送路径：

1. **私有协议长连 / Socket.IO**：`MailClientEngine/protocol/socketio_client.cpp` 在调试路径中出现 **272 次**（全工程最高频的单个文件），说明 Socket.IO 是主力实时通道，且被大量实例化（每个连接/重连点）。
2. **EWS Push**：`EWSPushmailClient`。
3. **Boost.Beast WebSocket**：符号中 `boost::beast::websocket::stream` 系列极多（数百个模板实例），属于库自带，不一定全部被业务使用。

**推断**：新邮件到达、标签变更、日程邀请等实时事件走 Socket.IO；Exchange 账号走 EWS Push；两者都失败时退化为定时轮询（`checkMailsServerStatus`）。

## 4. 文件夹与邮件的同步模型

从符号可还原出同步的关键设计：

```
_folderSyncOrder / _folderSyncOrderDownload / _folderSyncOrderUpload
_parseFolderRevFromServer          // 文件夹版本号(rev)比较
autoDoMoveMails / autoMoveMails    // 服务端规则触发的自动移动
checkMailsServerStatus
```

**推断**：采用"**文件夹级版本号 + 增量命令序列**"的同步模型：
- 服务器为每个文件夹维护 `rev`；
- 客户端比较本地 `rev` 与服务器 `rev`，只拉差异；
- 邮箱操作（移动/删除/标记）以"命令"形式排队，支持上下行双向（`Download`/`Upload`）；
- 离线期间的操作在恢复后重放。

这套模型同时解释了为什么 IMAP 需要 `ImapCommonCmdContext`（834 符号）——要把 IMAP 的 UID/序列号语义映射到统一模型上。

## 6. 服务端 REST/JSON 接口形态

私有协议在 HTTP 层暴露为 `/<版本>/s/json?func=<命名空间>:<方法>`：

| 路径 | 方法 |
|---|---|
| `/s/json?func=user:login` | 登录 |
| `/s/json?func=user:getPasswordKey` | 取密码加密公钥 |
| `/s/json?func=user:getPasswordURL` | 取改密链接 |
| `/s/json?func=user:getTempSession` | 临时会话（访客/免登录场景） |
| `/s/json?func=user:listAppPwds` / `addAppPwd` / `deleteAppPwds` | 应用专用密码（供 IMAP/SMTP/EWS 用） |
| `/s/json?func=user:getAttrs` | 用户属性 |
| `/s/json?func=user:generateVerifyCodeImage` | 图形验证码 |
| `/s/json?func=user:generateDeviceCertToken` | 设备证书 token（SM2 登录） |
| `/s/json?func=global:options` | 全局配置 |
| `/s/json?func=global:verify` | 校验 |
| `/s/json?func=global:getWelcomePageBulletin` | 欢迎页公告 |
| `/s?func=mbox:getComposeData&sid=&composeId=&attachId=` | 写信数据 |
| `mbox:compose` / `mbox:forwardMessages` / `mbox:deleteMessages` / `mbox:deleteFolders` / `mbox:createUserFolders` / `mbox:getAllFolders` / `mbox:getComposeInfo` / `mbox:listMessages` / `mbox:listMessagesV1` / `mbox:emptyFolder` | 邮件与文件夹操作 |
| `mbox:readMessage` / `mbox:getMessageData` / `mbox:getMessageInfos` | 读信 |
| `cim.user:getLunkrMailData` | 取 Lunkr IM 相关邮件数据 |

**观察**：接口命名空间是 `user:` / `mbox:` / `global:` / `cim.user:` / `calendar:`（`calendar:UID` 出现在字符串中）。这是 Coremail 服务端一贯的 `func=<ns>:<action>` 风格。

**推断**：`getPasswordKey` → RSA 公钥；`getPasswordURL` → 服务端托管的改密页（走浏览器 SSO，见 `coremail/06`）。`listAppPwds`/`addAppPwd` 的存在说明**客户端可以在服务端生成"应用专用密码"**，再拿去配 IMAP/SMTP——这是应对"主密码不能给第三方客户端"的常见做法。

### 6.1 私有协议的 HTTP 头（反编译确认）

`ProtocolContext_Coremail::initCoremailHttpClientDefaultHeader`（`0x1010e3a88`，证据 `ev_b4f7955c3fcae60a06719abfa16e439f5ccf6a3682a48a63670f50c10e26896c`）会为每个请求写入固定头：

| 头 | 值 | 说明 |
|---|---|---|
| `Accept` | `text/x-json,application/x-cm-json,application/json` | 三种响应格式都接受 |
| `X-CM-SERVICE` | `L-CMClient` | 服务标识（Lunkr/Coremail 客户端） |
| `X-CM-CONTROL-AGENT` | 全局配置值（非空时才写） | 管控/代理标识 |
| `X-CM-AIR-VERSION` | `DAT_104dcff10`（版本串） | Air 版本 |
| `X-CM-AIR-FEATURES` | `tz` | 能力协商，目前只声明时区 |

`make_request(func, var, bool, longlong, string const&)`（`0x1010e628c`）是请求组装核心，其中还能看到：

- `X-CM-AUTH-SID`（`0x104921352`）——**会话 SID 以独立头传递**，不只靠 Cookie；
- `Range: bytes=%d-`（字符串 `"bytes=%d-"`）——**正文分段下载**，与 `get_mail` 的 `offset`/`size` 参数对应；
- `"/lunkr-plugins"` 路径常量——Lunkr 插件路由；
- Content-Type 由三个函数决定（见 `15`）：
  - `application/json;charset=UTF-8`（普通）
  - `text/x-json;charset=UTF-8;tz=UTC;useTypeCastExtension=1`（POST JSON，带类型强转开关）
  - `application/x-cm-json;charset=UTF-8;tz=UTC`（Coremail 私有 MIME）

其他在二进制中出现的头（按用途分组，非本次反编译逐个确认写入点）：

| 组 | 头 |
|---|---|
| 客户端标识 | `X-CMClient-Version`、`X-Coremail-Locale`、`X-CM-HeaderCharset` |
| 同步 | `X-CM-SYNCSTATE`、`X-CM-CHECKSUM`、`X-CM-OABCACHE` |
| 安全 | `x-cm-smime`、`x-cm-smime-version`、`x-cm-secmail`、`x-cm-securitylevel`、`X-CM-CACBANNER` |
| 日历/日程 | `X-COREMAIL-BODYTYPE`、`X-COREMAIL-ALLDAYEVENT`、`X-COREMAIL-SENSITIVITY`、`X-COREMAIL-BUSYSTATUS`、`X-COREMAIL-MEETINGSTATUS`、`X-COREMAIL-REPLYTIME`、`X-COREMAIL-RESPONSETYPE`、`X-COREMAIL-DISALLOWNEWTIMEPROPOSAL`、`X-COREMAIL-ONLINEMEETINGCONFLINK`、`X-COREMAIL-ONLINEMEETINGEXTERNALLINK`、`X-COREMAIL-NEXTACTIVETIME` |
| 其他 | `X-CM-Forward-Sender`、`X-CM-BATCHSEND`、`x-cm-attr`、`x-cm-extinfo`、`X-CM-ScheduleDate` |

`X-CM-CHECKSUM` 的存在值得注意：说明**请求/响应带校验和**，用于检测传输损坏或中间篡改（具体算法未反编译）。

## 7. 内置服务商预设

二进制里硬编码了一批国内/国际邮箱的 IMAP/SMTP 组合（用于"添加其他邮箱账号"时的自动填充）：

```
imaps://imap.qq.com;smtps://smtp.qq.com
imaps://imap.163.com;smtps://smtp.163.com
imaps://imap.126.com;smtps://smtp.126.com
imaps://imap.263.net;smtps://smtp.263.net（及 imap.263.net.cn）
imaps://imap.21cn.com;smtps://smtp.21cn.com
imaps://imap.sina.com;smtps://smtp.sina.com（及 imap.sina.cn）
imaps://imap.sohu.com;smtps://smtp.sohu.com
imaps://imap.tom.com;smtps://smtp.tom.com
imaps://imap.china.com;smtps://smtp.china.com
imaps://imap.mail.yahoo.com;smtps://smtp.mail.yahoo.com（及 .com.cn）
imaps://imap-mail.outlook.com;smtp://smtp-mail.outlook.com      ← 注意：smtp 未加密
imap://imap.139.com;smtp://smtp.139.com                          ← 明文
imaps://imap.x263.net;smtps://smtp.x263.net
```

两个细节值得注意：
- Outlook 预设的 SMTP 用了**明文 `smtp://`**（应为 587 STARTTLS，属于预设配置的瑕疵）；
- 139 邮箱预设**连 IMAP 都是明文**。

**推断**：这些是历史遗留的预设值，未被清理；如果用户直接用预设且不手动改加密方式，会产生明文传输风险。

## 9. 线程与并发要点

- `MailEngine` 以 `shared_ptr` 传递，回调携带 `MailEngine` 引用（`reloadCoremailAIHubSettings(shared_ptr<MailEngine>, ...)`），说明**引擎生命周期由引用计数管理**，账号删/登出时靠 shared_ptr 释放。
- 大量 `ara::internal::auto_del_ref<T>` 出现在析构符号中——自研的引用计数辅助。
- 协议回调都是异步，**推断**有独立 IO 线程 + 主线程投递（`JsCallbackEvent` 通过 `wxEvtHandler` 投递回主线程即为例证）。
