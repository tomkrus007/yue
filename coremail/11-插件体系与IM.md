# 插件体系与 IM

## 1. 插件是"编译期静态扩展点"，不是动态库

`Plugin` 命名空间有 602 个符号，但**没有任何插件加载相关的符号**（没有 `LoadLibrary` / `dlopen` 的插件管理、没有 `.dylib` 扫描）。所有 `Plugin_*` 都是**编译进主二进制、启动时 `init()` 注册到框架**的模块。

证据：每个插件都有 `init` 方法（`Plugin_ExtAuth::init`、`Plugin_ExternalURL::init`、`Plugin_ExtTemplate::init`、`Plugin_Monitor::init`、`Plugin_SMIME::init`、`Plugin_IM::init`），且都是无参/少参。

```cpp
// 统一模式
class Plugin_Xxx {
    static void init();     // 注册菜单项/工具栏/事件监听
};
```

**推断**：`MainFrame` 启动时按固定顺序调用各插件的 `init()`，插件通过注册回调把自己的 UI 入口挂上去。这是"**单体应用内的模块化**"，而不是可扩展的插件系统。

### 2.1 `Plugin_ExternalURL` 的规则引擎

```cpp
struct Rule;
checkURL(url)
parseTarget(url)          // 解析出目标（内嵌浏览器 / 系统浏览器 / 特定 App）
replaceURLParams(url)     // 变量替换（如 ${uid}）
```

**推断**：这是一个**可配置的外链白名单/路由规则**，决定点击链接时是：
- 用内嵌 CEF 打开；
- 用系统默认浏览器打开；
- 交给某个 App 的 scheme（`lunkr://`、`wxWork://`、`notes://`）。

相关字符串：`notes://,lunkr://,mailto://,cmmailto://`。

### 2.2 `Plugin_ExtAuth`

```cpp
accountNeedExtAuthLogin()      // 该账号是否需要外部认证
supportNoPasswordLogin()       // 是否支持免密登录
supportCreateAccount()         // 能否通过外部认证创建账号
onCreateAccount()
onAuthLogin()
onIdle()
doMessage()
```

**推断**：企业 SSO 场景下，登录窗口会多出一个"用企业账号登录"的按钮，点击后走 `cmsso`（见 `coremail/06`），成功后**自动创建本地账号**（`onCreateAccount`）。`onIdle` 说明认证流程有后台轮询/心跳。

### 2.3 `Plugin_ExtTemplate`

`ComposeTemplate` + `init` —— **外部配置的信纸/模板**。

**推断**：企业可下发统一签名/信纸模板，客户端从服务端或本地目录加载。与 `LANG_TEMPLATE_*`（35 条文案）、`conf/template.csv` 呼应。

### 2.4 `Plugin_Monitor`

只有 `init` 和 `onStartCompose`。**推断**：这是一个埋点/监控挂钩，在写信开始时上报（配合 `la.js` 的 `startCompose` 事件）。

## 3. IM 体系（最复杂的一块）

### 3.1 配置驱动

`app/plugin/setting_im.js` 定义了 IM 后端列表（**注意：这是 JSON 但文件名是 .js**，且内容是 Windows 路径）：

```json
{
  "im": [
    {
      "group_chat_label": "#LANG_IM_WXWORK",
      "coremail_backend_query": "/lunkr-plugins/weixin/getUserIdByEmail",
      "coremail_backend_create": "/lunkr-plugins/weixin/createGroup",
      "coremail_backend_local": "wxWork://",
      "condition_user_attribute": "support_create_wxwork_group",
      "condition_user_attribute_value": "1",
      "installed": ["{{reg:HKCU\\Software\\Tencent\\WXWork\\Executable}}"],
      "chat_icon": "discuss.ico"
    },
    {
      "type": "CIM",
      "chat_label": "#LANG_IM_LUNKR_CHAT",
      "group_chat_label": "#LANG_IM_LUNKR_GROUP",
      "installed": [
        "{{reg:HKLM\\Software\\Lunkr\\InstallPath}}\\lunkr.exe",
        "{{reg:HKCR\\lunkr\\shell\\open\\command\\}}"
      ],
      "chat_icon": "lunkr.ico"
    }
  ]
}
```

**这是一个明显的跨平台移植缺陷**：`installed` 字段全是 **Windows 注册表探测**（`HKCU\Software\Tencent\WXWork`、`HKLM\Software\Lunkr`）。在 macOS 上这些 `{{reg:...}}` 永远解析失败，意味着：
- "检测第三方 IM 是否已安装"的功能在 macOS 上**恒为未安装**；
- 所以"从邮件发起企业微信/ Lunkr 聊天"的入口在 macOS 上可能**永不显示**，或退化为提示"未安装"。

**推断**：官方对 macOS 版 IM 集成的投入明显低于 Windows 版，这是"同一份配置文件跨平台复用"的直接后果。

### 3.2 三种 IM 后端

| 后端 | 类型 | 本地 scheme | 服务端接口 |
|---|---|---|---|
| 企业微信 | 外部（`WXWork`） | `wxWork://` | `/lunkr-plugins/weixin/getUserIdByEmail`、`createGroup` |
| Lunkr（CIM） | 自有 | `lunkr://` | `/lunkr/s/json?func=cim.user:getLunkrMailData` |
| 默认 IM | 内置 | — | `Plugin_IM::defaultCIMCheck`、`defaultWxCheck` |

`Plugin_IM` 的方法名揭示了双后端结构：

```cpp
defaultCIMCheck()      // 默认用 CIM？
defaultWxCheck()       // 默认用企业微信？
initDefaultIM()
supportChatWith / supportChatWithGroup / supportChatWithGroupFromToolbar / supportChatWithMySelf
chatWithByURL / chatWithByCoremailBackend
initChatURLVar / initGroupChatURLVar
```

**推断**：
- `chatWithByCoremailBackend` = 通过服务端接口建群/查人（企业微信路径）；
- `chatWithByURL` = 直接拼 scheme URL（Lunkr 路径）；
- `chatWithMySelf` = 给自己发消息（备忘/文件传输助手）；
- `g_nNextCmdIDOffset` 是命令 ID 分配器，说明 IM 调用走的是**异步命令编号**机制。

### 3.3 Lunkr 服务端

```
https://pcmail.coremail.cn/lunkr
https://pcmail.coremail.cn/lunkr/s/json?func=cim.common:checkVersion
https://pcmail.coremail.cn/lunkr/s/json?func=cim.common:dlFeedback&u=
/coremailclient/lunkrserverconfig.jsp        ← 从租户服务器拉 Lunkr 配置
https://lunkr.coremail.cn/log/report
https://help-lunkr.coremail.cn/
/lunkr-plugins/weixin/...                    ← 租户服务器上的微信插件代理
```

**推断**的架构：

```
客户端 ──(lunkrserverconfig.jsp)──> 租户邮件服务器
                                   │ 返回 Lunkr 服务地址/版本/开关
客户端 ──(cim.common:checkVersion)──> https://pcmail.coremail.cn/lunkr   (SaaS 公共实例)
客户端 ──(cim.user:getLunkrMailData)──> 同上（取邮件关联的 IM 数据）
```

即 **Lunkr 是独立的 SaaS 服务，客户端通过租户服务器拿到接入配置**。

注意 `/lunkrcm07.rd.mt` —— 又一个研发域名，与 `cmsso://fasoncm.rd.mt` 同类，说明研发配置被打进了生产包。

### 3.4 Lunkr 与 AI 的关系

```
LANG_AIASSIST_SETTING_LUNKR=Lunkr Assistant
AIAssist::supportLunkrAIAssist
```

**推断**：Lunkr 产品线同时提供 **IM 与 AI 助手**，且 Coremail 的 AI 能力部分依赖 Lunkr 服务（"Lunkr Assistant"是 AI provider 之一）。这解释了为什么 AI 与 IM 在代码上耦合（同一个 `Plugin` 层，同一套 SaaS 后端）。

## 4. 插件桥（WebView 侧）

`app/plugin/webview/plugin.js` 是给**第三方网页插件**用的桥：

```js
function callPC(funcName, args, needLog)  // 同 template/utils/callPC.js
var callBack = {};
function registerCallback(func)  { ++callBackNum; var res = "func"+callBackNum; callBack[res]=func; return res; }
function callCallback(name, res) { var f = callBack[name]; if (f) f(res); delete callBack[name]; }

var CMPlugin = {
  close: function() { callPC("closeWin"); },
  getAttributes: ...,
  ...
};
```

关键 API：

| API | 作用 |
|---|---|
| `CMPlugin.close()` | 关闭当前插件窗口 |
| `CMPlugin.getAttributes()` | 读取插件属性（宿主注入的上下文） |
| `registerCallback/callCallback` | 请求-响应配对（一次性回调，用完即删） |

`plugin/webview/readmail.js` 内容只有 `{}`（3 字节）—— **占位文件**，说明这套"网页插件"机制目前基本没有实际使用，只是框架预留。

## 5. 与 wxWidgets AUI 的关系

`3rd/wx/src/aui` 在调试路径中出现 6 次，且 `Plugin_Splitter` 存在，**推断**主窗口布局用 wxAUI（Advanced User Interface，可停靠面板），所以"分栏"是一个可拖拽、可保存布局的插件。

这解释了 `global_gui.conf` 的存在——保存窗口布局/列宽等 GUI 状态。
