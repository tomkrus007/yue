# AI 助手

## 1. 总体结构

AI 能力分三层：

```
AIAssist (ara::singleton, 单例)          ← 全局策略：是否启用、走哪个 provider
├── AIAssist::supportAI / supportAIExtension
├── AIAssist::getAIType / setAIType / getAITypeName
├── AIAssist::enableAIAssist / enableAIAssistByEng
├── AIAssist::isAdvanceAIAssist / isAdvanceAIAssistByEng
├── AIAssist::supportLunkrAIAssist / supportKylinKartAIAssist
├── AIAssist::hasReadAndAgreeStatement    ← 首次使用需同意声明
└── AIAssist::getAILocalAccessPrefix      ← 本地访问前缀

AISettingFactoryImp (工厂)               ← 按名字创建 provider
└── registerNameOnly(...)

AISetting_<provider> (策略实现)          ← 每个厂商一个子类
├── makeRequest(...)                     ← 组请求
├── onResult(...)                        ← 解响应
└── listSubModule(...)                   ← 可用模型/子模块列表
```

`AISettingFactoryImp::registerNameOnly` 说明 provider 注册只需要名字，具体行为由子类多态提供——典型的**策略模式 + 注册表**。

## 3. 托管模式：AIHub

```
AIHubURL
/aihub/
reloadCoremailAIHubSettings
loadCoremailAIHubSettings
Protocol::AIHubSetting (21 符号)
```

**推断**：`AIHub` 是 Coremail 服务端提供的**统一 AI 网关**：

- 客户端不直连模型厂商，而是把请求发到 `/aihub/`；
- 优势：企业统一计费、统一审计、密钥不下发到客户端；
- `reloadCoremailAIHubSettings` 从服务端拉取当前租户可用的 provider/模型/prompt 策略。

这与"Lunkr Assistant / Coremail Assistant"两个托管选项对应——**Lunkr 是 Coremail 的 IM/AI 产品线名**（见 `coremail/11`）。

### 3.0 反编译确认的调用链（第二版）

`Protocol::coremailAIHubCall(MailEngine, func, model, prompt, callback)`（`0x10123eb60`，证据 `ev_5dd66e332e501829e84979bcac4e8eaca04a6c59b4417a0844780e3476698d27`）：

```cpp
if (!MailEngine::isCoremailProtocol(engine)) return;      // 只对 Coremail 协议账号生效
sid    = MailEngine::getCoremailSessionID();
cookie = MailEngine::getCoremailCookie();
header = ProtocolContext_Coremail::initCoremailHttpClientDefaultHeader();
header["Cookie"] = cookie;
body = { "header": { <header 的每个 k:v> },
         "Accept": "text/event-stream,text/x-json,application/x-cm-json,application/json" };
AIClient::aiCall(AIHubSetting(...), func, model, callback);
```

由此可确认：

1. **AIHub 请求复用 Coremail 会话 Cookie**（`getCoremailCookie`），不走独立的 API Key；
2. **请求头被复制进 JSON body**（`body.header`），这不常见——说明网关侧会读取 body 里的 header 做二次决策（**推断**用于服务端审计/多租户路由）；
3. **支持 SSE 流式**：Accept 里明确带 `text/event-stream`，与 `4.2` 的流式渲染对应；
4. 非 Coremail 协议账号（IMAP/POP3/EWS）**不会走 AIHub**。

`Protocol::AIHubSetting::makeRequest`（`0x10123be80`，59 KB 伪代码，证据 `ev_d24ab005d122f98300dacaeb6896ca9e1c510a78b0786ad47256994e94f901a2`）里出现的路径常量是 **`/aihub/`**，URL 由账号服务器地址 + `AIHubURL` 配置拼成（与上述推断一致）。

### 3.1 Prompt 策略

```
AIPromptSetting
```

**推断**：Prompt 模板可由服务端下发（`AIHubSetting` 里带 prompt），客户端只负责填充变量（邮件正文、收件人等）。这样企业可以统一调整 AI 行为而不发版。

### 4.1 请求协议：`aiCall` / `aihubResponse`

`template/lib/cmAI/cmAI.js` 是 AI 功能的前端核心（压缩后仍可读）：

```js
requestAihub({ qrySN, qrySNPrefix, content, url, $out, callback, handler, trigger, isHtml }) {
  qrySN = qrySN || `${qrySNPrefix}:${qrySNRandom}:${qrySNCount++}`;
  // 注册一次性回调 window.app[funcName]
  // 发送 callPC("aiCall", {...})
  // 响应校验 t.qrySN === qrySN && t.code === "S_OK"
}
```

关键点：

1. **`qrySN`（query serial number）**：`前缀:随机数:自增计数`，用于**多路并发请求的响应配对**；
2. **回调函数动态挂到 `window.app[funcN]`**，由原生侧回调；
3. **`code === "S_OK"`** 是成功约定（不是 HTTP 状态码，是业务码）；
4. `isHtml: 2` 默认——**流式返回**（值 2 表示分段/流式，推断）；
5. 有 `cmAI.cancel(qrySN)` → `callPC("aiCancel", {qrySN})`，支持请求级取消。

### 4.2 流式渲染

```js
cmAI.TRANSLATED = "translated";
cmAI.cursorTpl = "<span class=cursor>|</span>";
```

**推断**：AI 输出是**逐段追加 + 光标动画**的流式体验，不是等全文返回。`cursorTpl` 说明用一个闪烁 `|` 表示"正在生成"。

### 4.3 邮件内容获取

```js
prepareMailContent({ callback }) {
  const e = getMailContent();           // 从 readMail 的 appFunc 取正文
  callback && callback([{ body: e || "" }]);
}
```

AI 请求的上下文**直接取当前打开邮件的正文**，并转成 `[{body}]` 的数组结构（支持多段/多封）。

## 5. Token 计费埋点（重要观察）

```js
const trackTokenUsage = (t, e, r = "") =>
  e && window.la && t.tokenUsage && t.tokenUsage.total_token &&
  la.track(`${e}/token-AI_${r}`, {
    log: { val: t.tokenUsage.total_token, op: "3" }
  });
```

- 每次 AI 响应都读 `var.tokenUsage.total_token`；
- 通过 `la.track` 上报到埋点系统；
- 事件名格式：`<trigger>/token-AI_<feature>`，例如 `translate/token-AI_translate`；
- `op: "3"` 是埋点操作码（见 `coremail/12`）。

**推断**：token 用量上报用于**企业成本分摊/配额控制**，不只是产品分析。这也解释了为什么 AI 要按账号授权（`PERMISSIONS_ACCOUNT`）。

## 6. 错误处理

```js
cmAI.checkAIError(t.code)
```

从 `console.log("aihubError--> " + JSON.stringify(t))` 的结构推断，错误返回是 `{code, var, msg}` 三元组，与本地 SDK 的响应格式一致（见 `coremail/10`）。

**推断**：AI 与 SDK 共用同一套 `ara::var` 响应信封，`code === "S_OK"` 表示成功，其余为业务错误码。

## 8. 直连 provider 的端点形态（第二版补充）

反编译 + 字符串确认，`AISetting_*` 子类走 **OpenAI 兼容协议**（`makeRequest` 只有 `openai` / `azure` / `qwen` / `openailike` 有独立实现，其余复用）：

| 端点 | 出现位置 | 适用 provider |
|---|---|---|
| `/v1/chat/completions` | `0x104920b3c` | OpenAI / Azure / DeepSeek / Moonshot / SiliconFlow / Qwen / Spark / openailike / Kart |
| `/v1/models` | `0x104920d2c` | 列模型（`AIClient::openAIListModels`，日志 `Query AI models : URL: %s, retcode: %d`） |
| `/api/embeddings` | `0x104920b51` | **Ollama**（本地/自托管） |

`AIClient::aiCall` 系列（`0x1010ca920` / `0x1010caba0`）只做 **provider 分发**，不含协议细节；`aiComplete` / `aiGenerate` / `aiEmbedding` 分别对应补全、生成、向量化三类请求。`beginSession` / `endSession` / `clearSession` 说明**会话可以复用**（多轮对话保持上下文）。

这印证了第一版的判断：**除 AIHub 托管外，其余 provider 全部是 OpenAI Chat Completions 兼容格式**，因此"支持 10 个 provider"本质是"10 套 base_url + 鉴权头 + 少量字段差异"。
