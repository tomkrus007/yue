## 2. 日历

### 2.1 数据模型

```cpp
class CalendarData;                        // 3963
enum class CalendarSyncOption;             // 969
class CalendarManager;                     // 662
class CalendarFolder;                      // 585
class CalendarFolderAccessMgrDlg;          // 259（文件夹权限管理）
struct CalendarSyncFailureRecord;          // 243（同步失败记录 → 有重试机制）
class CalendarDataToServer;                // 238（上行序列化）
class ScheduleWithRichDataInServer;        // 237（服务端富数据）
struct ScheduleTimeInfo;                   // 236
class CalendarRemindDlg;                   // 385（提醒）
class CalendarSearchResultPanel;           // 340（日程搜索）
```

**关键推断**：
- `CalendarSyncFailureRecord` 存在 → 日历同步**不是"失败就算了"**，会记录失败条目并重试；
- `CalendarDataToServer` 与 `ScheduleWithRichDataInServer` 成对 → 客户端与服务端之间有一套**富文本日程**的序列化协议；
- `CalendarFolderAccessMgrDlg` + 文案 `LANG_CALENDAR_SHAREFOLDER_READONLY/EDIT/SUBSCRIBE` → **日历文件夹级权限**（只读/可编辑/订阅）。

### 2.2 循环日程

| 证据 | 说明 |
|---|---|
| `IcsVarUtilities` | iCalendar 变量工具 |
| `calendar_utility` | 日历工具函数 |
| `RruleStr`（SDK 文档） | RFC 5545 循环规则字符串 |
| `ExceptionsData`（SDK 文档） | 例外日期 |
| `syncRecurrenceExceptionsToAttendees` | **循环日程的例外要同步给所有参会人** |
| `template/recurrence/` | 循环规则编辑 UI（**独立 CEF 页面**） |
| `LANG_CALENDAR_OPEN_RECURRENT_MSG` / `_SCHEDULE_MSG` / `FORWARD_RECURRENT_MSG` / `DELETE_RECURRENT_MSG` / `CANCEL_RECURRENT_MSG` | 针对"循环日程邮件"的 5 种操作 |

**推断**：循环日程被视为**一等公民**，连"转发/删除/取消"都区分"单次 vs 整个系列"。`template/recurrence/` 是独立的 CEF 视图，说明编辑循环规则用的是网页控件（富交互），而不是原生对话框。

### 2.3 会议室与忙闲

```
checkMeetingRoomConflicts / checkMeetingRoomConflictsByRoom
checkSchedulesConflicts
checkUserFreeBusyConflict
LANG_CALENDAR_SEARCH_RANGE_*（7 种时间范围）
enable_show_calendar_busy_idle: true（privatization-setting.js）
```

`template/bookmeeting/` 下有 `bookmeeting.html` 与 **`querymemberbusy.html`**——两个独立 WebView，分别负责"预订会议室"和"查询成员忙闲"。

**推断**：会议室预订是**服务端冲突检测 + 客户端 UI**的组合，且忙闲查询是单独页面（可能因为要显示复杂的成员×时间段矩阵）。

### 2.4 时区

`tzdata/` 是完整的 IANA 数据库（`africa`…`southamerica`、`zoneinfo`、`leapseconds`、`version`），外加 `windowsZones.xml`（Windows 时区名 ↔ IANA 映射）。

配置项：

```json
"support_standard_timeZone_version": {
    "forward_modify_hours": 8,
    "xt_minimum_versions": ["5.0.16", "6.0.5"]
}
```

**推断**：客户端会**校验服务端的时区数据版本**，低于最低版本时提示升级（`forward_modify_hours: 8` 可能是默认时区偏移东八区）。

## 3. 联系人

### 3.1 分层

| 层 | 符号/配置 | 说明 |
|---|---|---|
| `Contact` | 2464 | 联系人实体 |
| `ContactFrame` | 337 | 通讯录窗口 |
| `ContactInfoItemID` | 227 | 字段 ID（对应 `contacts-attributes.js`） |
| `AppendPersonalContact` | 协议方法 | 个人联系人写入 |
| `autoMatchContactFromWeb`(18) / `autoMatchContactFromWebEx`(9) | 协议方法 | **收件人补全走服务端** |
| `getOrgContactsInfo`(8) | 协议方法 | 组织架构成员 |

### 3.2 补全优先级（来自配置）

```json
// conf/address-setting.js
"automatch_sort_order": ["history", "personalgroup", "personal", "orgcontact", "orggroup"],
"orgcontactfirst": true,
"history_record_known_user": true,
"history_record_rcpt": false,
"merge_result": true,
"string_range_search": true,
"org_cache_limit": 0,
"auto_sync_addr_start_program": true,
"auto_sync_addr_timer_check_interval_hour": 2,
"display_fulldn_mode": 2,
"org_type_order": ["U", "L", "X", "R"]
```

逐条解读：

- **补全顺序**：历史记录 → 个人分组 → 个人联系人 → 组织联系人 → 组织分组。`orgcontactfirst: true` 与之**冲突**（前者把 org 放最后）。**推断**：`orgcontactfirst` 是旧开关，已被 `automatch_sort_order` 取代，遗留未删。
- `history_record_rcpt: false`：**不记录**普通收件人到历史（只记录"已知用户"），这是隐私设计。
- `string_range_search: true`：支持子串/范围匹配（不是前缀匹配）。
- `auto_sync_addr_timer_check_interval_hour: 2`：组织架构**每 2 小时增量同步**。
- `org_cache_limit: 0`：不限制缓存条目数。
- `org_type_order: ["U","L","X","R"]`：组织类型排序（**推断** U=User, L=Leader/Department, X=外部, R=根/Region）。

### 3.3 可见字段

```json
// conf/contacts-attributes.js
[
  {"id":"duty","display":true,"optional":true},
  {"id":"company_phone","display":true},
  {"id":"alias_emails","display":true,"optional":true},
  {"id":"fax_number","display":false},
  {"id":"home_phone","display":false},
  {"id":"address","display":false},
  {"id":"zipcode","display":false}
]
```

**推断**：这是**企业场景精简版**通讯录——只显示职务、公司电话、别名邮箱；家庭电话/地址/邮编默认隐藏（隐私或客户不需要）。`optional: true` 表示导入时可不填。

## 4. 过滤器（收信规则）

`Filter` 2187 + `Filters` 935 + `FiltersDlg` 780 + `FilterDlg` 441 + `FiltersContext` 497 + `FilterEvent` 377 + `FilterReq` 235 + `FilterDlgNameSpace` 313。

`FilterEvent` / `FilterReq` 说明过滤器有**事件驱动**成分（来信时实时匹配），而非纯服务端规则。

配套：

```cpp
syncOrCreateFolderInFilter     // 过滤器引用的文件夹不存在时自动创建
autoDoMoveMails / autoMoveMails // 规则命中后的自动移动
```

`LANG_MANAGEFILTERS`（135 条文案）+ `LANG_NEWFILTER`（107 条）说明过滤器编辑器相当复杂（多条件 + 多动作 + 测试）。

**推断**：过滤器**同时存在于客户端与服务端**——客户端版用于离线/本地规则，服务端版用于 Web 端一致行为。`syncOrCreateFolderInFilter` 暗示客户端会把自己的规则同步到服务端（或反之）。

## 6. 邮件撤回（Recall）

```
deleteLocalEmail_websocket_recallmail_search    ← 字符串（函数名+业务名拼接）
LANG_RECALLMAIL_*（21 条）
LANG_VIEWRECALLMAIL_*（21 条）
```

**推断**的三段式实现：

1. **WebSocket 通知**：服务端通过推送通道告知"某封邮件被撤回"；
2. **本地搜索定位**：`recallmail_search` 用原始 Message-ID / 唯一标识在本地存储中定位；
3. **本地删除/标记**：删掉本地副本，或在原位置插一条"已被撤回"占位。

`LANG_VIEWRECALLMAIL_*` 说明撤回后仍可查看（服务端保留副本供审计）。
