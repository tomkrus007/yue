# 依赖与许可

## 1. 链接模型（观测）

`otool -L cmclient` 共 **22 个依赖项**，其中 **1 个自带 dylib + 21 个系统库**：

```
@rpath/libgmssl.3.dylib               ← 唯一非系统动态库
@rpath → @executable_path/            ← 单一 rpath

系统库（节选）：
Foundation / Cocoa / AppKit / Carbon / CoreFoundation / CoreServices /
CoreText / CoreGraphics / QuartzCore / ApplicationServices /
AudioToolbox / IOKit / Security / WebKit / ImageIO / libiconv /
libexpat / libz / libc++ / libobjc / libSystem
```

**关键结论**：

1. **除 GmSSL 外全部静态链接**——包括 OpenSSL、Boost、Xapian、wxWidgets、ICU、sqlite3mc、CEF 的 C++ 包装层（`libcef_dll_wrapper`）。
2. **CEF 的 Chromium 本体不在 `otool -L` 里**：主二进制有 2,940 个**已定义**的 `Cef*` 符号（这是 CEF 的 C++ wrapper），但真正的 `libcef` 在运行时从 `../Frameworks/Chromium Embedded Framework.framework/Chromium Embedded Framework` **动态加载**（字符串 `../Frameworks` + `Chromium Embedded Framework.framework/Chromium Embedded Framework` 存在）。4 个 Helper（各 2.5 MB）也是同一模式——它们本身不含 Chromium，靠 dlopen 加载 160 MB 的 framework。
3. **链接了 `WebKit.framework`**：这是 wxWidgets 的 `wxWebView` 默认后端所需，说明即使主 UI 用 CEF，代码里仍保留 WebKit 路径（或 wx 库静态链接时带入了依赖）。
4. **`LSRequiresCarbon = true`**：仍有 Carbon 兼容层依赖（wxWidgets 的 macOS 传统路径）。

| 文件 | 大小 | 说明 |
|---|---|---|
| `libgmssl.3.1.dylib` | 819,712 | GmSSL 3.1 实体 |
| `libgmssl.3.dylib` | 819,712 | soname `libgmssl.3`（compatibility 3.0.0 / current 3.1.0） |
| `libgmssl.dylib` | 819,696 | 无版本号入口（少 16 字节的 install_name 差异） |

三份是同一库的三种命名，用于兼容不同链接期 soname。这是**手工维护产物**的痕迹（正常构建只需 symbolic link）。

### 3.1 缺失的许可文件（合规风险）

以下组件在二进制中存在，但 `licensing/` 里**没有**对应许可文件：

- **ICU**（`icu_78`，8,831 符号）——需要 Unicode License
- **GmSSL**（`libgmssl`）——需要 Apache-2.0
- **sqlite3mc** ——需要 MIT（sqlite3 + multiple-ciphers）
- **SQLite** ——Public Domain
- **rapidjson** ——MIT
- **rtf2html** ——未确认
- **libpst / pstsdk** ——通常 GPL/BSD 混合
- **hunspell**（拼写检查，若使用）——LGPL/MPL/GPL 三选

**观察**：`xapian` 是 **GPL-2.0+**，`wxWidgets` 是 **LGPL + 静态链接例外**。两者都以静态链接方式进入闭源商业软件，**合规上必须依赖各自的例外条款**：
- Xapian 是纯 GPL，**没有链接例外** → 静态链接进闭源商业软件在 GPL 解释下存在争议（这是本项目最明显的许可风险）；
- wxWidgets 的 "wxWindows Library Licence" **明确允许**以目标代码形式分发衍生作品（这是它被商业软件广泛使用的关键）。

**推断**：Coremail 可能持有 Xapian 的商业授权，或依赖"进程间通信"式的边界，但仅从包内证据（静态链接 + 无例外条款）看，这是一个**需要在法务层面确认**的点。

## 5. 二进制体积构成（估算）

| 段/组件 | 大小 | 说明 |
|---|---|---|
| `__text` | 35.4 MB | 代码（引擎 + wx + CEF wrapper + 静态库） |
| `__const` | 37.9 MB | 只读数据（可能是 ICU 数据、证书、字符串表、查找表） |
| 主二进制总计 | 114.8 MB | 未 strip，含 23 万符号 |
| CEF framework | 160.3 MB | Chromium |
| 4 个 Helper | 10 MB | 每个 2.5 MB（不含 Chromium） |
| GmSSL × 3 | 2.4 MB | |
| `app/` 资源 | ~10 MB | template 2.2+1.8+0.8 MB、dict 7 MB、locale、resource |
| **整包** | **374 MB** | |

**观察**：`__const` 比 `__text` 还大，这在普通应用里很罕见。**推断**主因是 **ICU 数据（ICU 78 的 data 表通常 30 MB 左右）被静态链入**，加上 Qt/wx 的资源表。这也解释了为什么 `icu_78` 有 8,831 个符号——它不是精简版 ICU。
