### 1.1 关键工具约束

- **REA 可用但无深度反编译器 provider**：`GHIDRA_INSTALL_DIR` 未设置，Hopper / IDA / Kuna 均不可用，因此**无法反编译函数体**，也无法获得伪代码。
- `inspect_macho` 的全量响应超过 10 MiB 限制，必须用 `detail:"summary"` 获取摘要证据，再通过 `inspect_analysis_view` 按 facet（`segments` / `dependencies` / `build_metadata` / `entrypoints`）分片读取。
- 摘要证据（`ev_f278...`）本身**不可**直接作为 `inspect_analysis_view` 的 `source`；必须使用其 `parent_evidence_id`（`ev_bb9e...`）。这是 REA 的 "summary receipt" 语义。

## 3. 方法论边界

### 3.1 字符串证据的固有偏差

1. **编译器会去重与合并字符串**，同一个字符串只出现一次，无法据此判断使用频率（本报告中用 `nm` 符号计数替代，但符号计数也受内联/模板实例化影响）。
2. **优化会消除字符串**。例如 `11328` 若以立即数形式存在，`strings` 找不到；`/sse` 路径同理。
3. **`strings` 默认按 UTF-8 解析，遇到二进制或非 ASCII 会中断**。本报告在遇到 `sort: Illegal byte sequence` 时改用 `LC_ALL=C grep -a`。
4. **调试路径只在开启 `-g` 时保留**。本二进制保留了大量 `.cpp` 路径，说明构建带调试信息——这是信息泄露，但不是所有字符串都有同等可信度。

### 3.2 符号证据的解读风险

- **模板实例化导致计数虚高**：`boost::asio` / `boost::beast` 的符号数量（数百到数千）**不代表业务使用量**，只代表库被链接。
- **`MailEngine` 17,492 个符号包含大量 lambda/模板**，不能直接当作"17k 个功能"。
- 本报告在使用符号计数时，尽量只做**同维度相对比较**（如"日历 > 联系人 > 过滤器"），不做绝对规模断言。

### 3.3 无法从静态证据得出的结论

以下问题**必须有运行时验证或反编译**才能回答，本报告一律标注为"未确认"：

| 问题 | 需要的证据 |
|---|---|
| 私有协议的具体帧格式 | 反编译 `CoremailClient` 或抓包 |
| SQLite 自定义 codec 的算法 | 反编译 `Database::_registerCustomEncryptMethod` |
| 邮件文件头格式 | 反编译 `MailFile::check_header` |
| 本地服务是否校验 Origin / token | 运行时抓包或反编译 |
| MCP 默认端口 | 反编译 `MCPSvr::start` |
| 升级包是否验签 | 反编译 `UpgradeContext` |
| AIHub 真实域名 | 运行时抓包 |
| IMAP IDLE 是否使用 | 反编译 `ImapClient` |

## 4. 明确标注的"推断"清单（汇总）

按可信度从高到低排列：

### 4.1 高可信（多处独立证据交叉验证）

| 推断 | 支撑证据 |
|---|---|
| 邮件列表是 wx 自绘控件，不是网页 | `maillist_html.cpp` 路径 + `LANG_MAILLIST_ITEM` 的 `<TEXT TYPE=3>` 自定义标记 |
| CEF 的 Chromium 本体运行时 dlopen | `otool -L` 无 CEF + 2,940 个已定义 Cef 符号 + `../Frameworks` 字符串 + Helper 仅 2.5 MB |
| 本地存储三层（SQLite + 加密文件 + Xapian） | `Database` / `MailStorage` / `MailIndex` 三个独立符号族 |
| 支持国密合规场景 | GmSSL + SM2/SM3/SM4 + `signAsRed` + 涉密提示文案 |
| AI 与 SDK/MCP 共用同一 HTTP 栈 | 同属 `Plugin_CommandServer` 家族 |
| 存在信创分支 | `uos_custom.css` / `kos_custom.css` / `kylinkart` / `key: public-version-air` |

### 4.2 中可信（单一证据 + 合理推理）

| 推断 | 支撑 |
|---|---|
| `account.dat/edat/sdat` 对应明文/加密/强加密 | `getPlainExtName`/`getEncExtName` + `Database::upgradeEnc` |
| 同步模型是"文件夹 rev + 增量命令" | `_parseFolderRevFromServer` + `_folderSyncOrderDownload/Upload` |
| 请求-响应用 `qrySN` 配对 | `cmAI.js` 的 `qrySN` 生成与校验逻辑 |
| 埋点与崩溃上报共用通道 | `report_*` 配置项与 `uploadTrackData` 交叉 |
| `privatization-setting.js` 的 hash 用于防篡改 | `LANG_SECURITY_SETTING_INVALID` + `hash` 字段并存 |
| `installed` 用 Windows 注册表探测导致 macOS 上 IM 入口失效 | `{{reg:HKLM\...}}` 出现在 macOS 包内 |

### 4.3 低可信（推测，需验证）

| 推断 | 问题 |
|---|---|
| `isHtml: 2` 表示流式 | 只有取值痕迹，无枚举定义 |
| `extra_calendar_features: 7` 是位掩码 | 7 = 三项全开是猜测 |
| `org_type_order: [U,L,X,R]` 的具体含义 | 只有单字母 |
| `forward_modify_hours: 8` 是东八区偏移 | 可能只是"提前 8 小时" |
| `start(int, unsigned long, unsigned long)` 后两个参数语义 | 无调用点可查 |

## 5. 本报告**没有**做的事

1. 没有运行应用（未登录真实账号，未产生网络流量）。
2. 没有反编译任何函数体。
3. 没有解密任何本地数据（无样本、无密钥）。
4. 没有分析 CEF framework 内部（Chromium 是公版，无需分析）。
5. 没有分析 iOS/Android/Windows 版本做对比。
6. 没有评估漏洞可利用性（仅列出**风险面**，未做 PoC）。

## 6. 复现与后续建议

### 6.1 若要继续深入（按性价比排序）

1. **配置 Ghidra**（`GHIDRA_INSTALL_DIR`）后重跑 REA，即可获得伪代码，可补齐本报告全部"未确认项"。
2. **运行时抓包**（Charles / mitmproxy + 安装根证书）：确认 AIHub 域名、私有协议 JSON 结构、SDK/MCP 是否有鉴权头。
3. **静态提取 `app/*.js` 全部内容**（`template/` 约 5 MB）：前端逻辑几乎完全可读，是理解桥接口语义的最佳来源。
4. **样本目录构造**：新建一个本地账号，观察 `~/Library/...` 下生成的文件，验证存储布局推断。
5. **`skills/` 工程直接跑通**：开启 SDK 后 `npx tsx api/list-accounts.ts`，即可验证 15 个接口的真实行为。

### 6.2 引用本报告时的建议

- 引用具体结论时，请连带引用该结论所在文件的**章节号**与该处的"证据"列；
- 标注为"推断"的内容**不要**当作事实转述；
- 涉及安全风险的结论（明文预设、无鉴权本地服务、ATS 关闭）应注明"基于静态证据，未经运行时验证"。
