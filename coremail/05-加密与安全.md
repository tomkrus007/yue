# 加密与安全体系

## 1. 两套密码学栈并存

| 栈 | 版本 | 用途 | 证据 |
|---|---|---|---|
| **OpenSSL** | 3.4.1 (2025-02-11) | TLS、通用对称/非对称、证书解析，且**已内置 SM2/SM3 provider** | `providers/implementations/asymciphers/sm2_enc.c`、`providers/implementations/digests/sm3_prov.c`、`providers/implementations/signature/sm2_sig.c` |
| **GmSSL** | 3.1（独立 dylib） | 国密专用：SM2 签名/加密、SM3 摘要、SM4 分组 | `libgmssl.3.1.dylib`（819,712 字节）、`crypto/sm2/sm2_crypt.c`、`crypto/ec/ecp_sm2p256.c` |

OpenSSL 3.x 自带 SM2 是 2021 年后的能力，而 GmSSL 是独立分发（`licensing/pole` 里可能另有说明）。**推断**：GmSSL 用于必须"国密合规"的路径（设备证书、国密加密邮件），OpenSSL 用于 TLS 与常规 S/MIME。两套 SM2 同时存在是渐进迁移的典型痕迹。

`libgmssl.3.dylib`、`libgmssl.3.1.dylib`、`libgmssl.dylib` 是同一库的三份（`.3` 与 `.3.1` 字节数相同，`.dylib` 少 16 字节——典型的 `install_name` 差异），说明为兼容不同链接期 soname 而重复放置。

## 2. 邮件级加密的三种引擎

`CoremailEngine::EncryptMail` 与 `DecryptMail` 各自派生三个实现：

| 引擎 | 加密类 | 解密类 | 含义 |
|---|---|---|---|
| 标准 S/MIME | `StdSMime_Encrypt` | `StdSMime_Decrypt` | 基于 X.509 证书的标准 S/MIME |
| 服务端 S/MIME | — | `ServerSMime_Decrypt` | 由服务端代管密钥/解密（**推断**：证书存在服务端，客户端只做展示） |
| Coremail 自有 | `CoremailAES_Encrypt` | `CoremailAES_Decrypt` | "Coremail 加密邮件"，口令/网关式 |

`DecryptMail` 的公共抽象方法（三个实现都有，说明是统一接口）：

```cpp
needDecode()
decode() / asyncDecrypt()
hasDecodedFile()
copyDecodedFile()
getDecryptEngineName()
_adjustStructure()
```

`DecryptVerifyResult` 携带 `getExtReason()` / `hasExtReason()` / `getSavePos()` / `setSavePos()` / `setSMimeEngName()`——**推断**解密结果是一个"带原因码 + 缓存位置 + 引擎名"的结构体，`SavePos` 用于定位解密后缓存在原邮件文件中的偏移。

### 2.1 Coremail 加密邮件（对外不可解）

`app/template/encrypt/cmaes.html` 是被加密邮件的**展示模板**：

```html
<div id="coremailEncryptedMail">
    这是一封由 {{FROM_TITLE}}<span id="coremailEncryptedMailSender">{{FROM}}</span>
    ...
```

含义很清楚：**收件人没有解密能力时，看到的是这个模板渲染的"占位正文"**，真实内容在附件/服务端。这也解释了 `LANG_DECRYPTMAIL_FAILT_REASON_NOCERT`：

> 解密证书未找到。请在 [账号管理 - 邮件安全 - S/MIME 加密] 中导入证书后重试。

以及 `LANG_DECRYPTMAIL_RMS_IPCERROR_RIGHT_NOT_GRANTED`——**出现了 `RMS`**（Windows Rights Management Services）。说明 Coremail 加密邮件可能对接 **微软 RMS/IRM 或国产同类权限管理服务**，`Plugin_SMIME` 就是它的挂载点。

## 3. S/MIME 全流程（有完整 UI 文案）

从 `locale/setting.zh_CN.txt` 可完整还原 S/MIME 的校验与错误分层：

| 文案键 | 内容 |
|---|---|
| `LANG_SMIME_VERIFY_OK` | 邮件签名验证成功 |
| `LANG_SMIME_VERIFY_CMSM_OK` | 邮件签名验证成功（**应用证书**） |
| `LANG_SMIME_VERIFY_CRCERR` | 邮件内容已被篡改 |
| `LANG_SMIME_VERIFY_CERTERR` | 签名证书格式不正确 |
| `LANG_SMIME_VERIFY_SENDERERR` | 证书邮件地址 ({1}) 与发件人 ({2}) 不一致 |
| `LANG_SMIME_VERIFY_TIMERANGERR` | 证书有效期时间与邮件时间不匹配 |
| `LANG_SMIME_VERIFY_CERT_REVOKED` | 证书已被撤销 |
| `LANG_SMIME_VERIFY_CERT_CHECKFAIL` | 证书校验失败 |

这套错误分类非常完整（含**证书撤销检查**、**时间戳对齐**、**发件人绑定**），说明 S/MIME 实现是"可用于合规审计"的级别，而不是花架子。

### 3.1 "应用证书"概念

`LANG_SMIME_VERIFY_CMSM_OK`（Coremail SM = CM-SM？）与 `LANG_SMIME_CREATE_CERTIFICATE_OK` 一起说明存在**两类证书**：

1. **标准 S/MIME 证书**（用户导入，或从 CA 申请）；
2. **Coremail"应用证书"/"邮件专用加密签名证书"**——客户端本地生成、自签发、仅用于邮件端到端加密与完整性校验，**不用于身份校验**（原文："不能用于用户身份的校验"）。

生成后会"**加密保存在本机中**"（对应 `MailStorageKeyManager` / `Database::_rekey` 的加密落盘）。

### 3.2 共享账号的证书使用

```
LANG_SMIME_SEND_SHARE_SENDER_NO_CERT=共享账号 [{1}] 没有加密签名证书...
LANG_SMIME_SEND_SHARE_SENDER_NO_CERT_USESELF=共享账号 [{1}] 没有加密签名证书，是否使用本账号证书签名？
LANG_SMIME_SEND_NONE_CONFACCOUNT_NO_CERT=非登录账号 [{1}] 没有加密签名证书...
```

说明客户端支持**多账号（共享账号 / 非登录账号）**，并明确区分"用哪个身份的证书签名"，且会提示风险。

### 3.3 收件人证书缺失的提示

```
LANG_SMIME_SEND_USER_HAS_NO_CERT=本地没有以上收件人的加密证书，他们收到邮件将无法解密查看邮件内容。
接收来自该收件人S/MIME签名邮件或导入该联系人的证书文件均可获得证书。
```

即：**证书靠"签名邮件回信"或"手动导入"获得**——标准 S/MIME 的 TOFU（trust-on-first-use）模型。

## 4. 设备证书与 SM2 登录

字符串证据（运行时日志）：

```
DeviceCert: supportAuthDeviceCert=false, skip SM2 keypair, user:%v
DeviceCert: supportAuthDeviceCert=true, generated SM2 keypair, user:%v, publicKey size:%v, hasPrivateKey:%v
DeviceCert: sending user:login request, user:%v, hasSm2PublicKey:%v, hasCertSignature:%v
```

配合接口：

```
/s/json?func=user:generateDeviceCertToken
```

**推断**的流程：

1. 首次登录（或满足服务端策略时），客户端**本地生成 SM2 密钥对**；
2. 私钥加密保存在本机（与 `MailStorageKeyManager` 同一套保护）；
3. 通过 `user:generateDeviceCertToken` 把公钥/设备信息交给服务端换 token；
4. 后续登录用设备证书签名替代（或辅助）口令，实现"免密/多因子"。

`LANG_DEVICE_QUERY_DLG_*`（"登录设备查询"、系统/名称/应用/最近登录时间/有效期/**永远有效**）说明用户可以在客户端里**查看并管理已授权的登录设备**。

## 5. 口令与凭据

| 机制 | 证据 |
|---|---|
| 登录口令 RSA 加密 | `user:getPasswordKey`（取公钥）+ `checkPasswordEncryptType` |
| 密码强度检查 | `checkPwdLevelInfo` |
| 应用专用密码 | `user:listAppPwds` / `addAppPwd` / `deleteAppPwds` |
| 改密链接 | `user:getPasswordURL` / `getPasswordURL4NewAccount` |
| 二次验证 | `LoginSecondAuthContext`：`TriggerLoginSecondAuth`、`SendSmsValidCode`、`SendVerifyCellCodeOnLogin`、`GetLoginSecondAuthImageCode`、`FinishGetLoginSecondAuthImageCode` |
| 图形码备份 | `Backup/RestoreLoginSecondAuthImgContext` |

`checkPasswordEncryptType` 的命名暗示**服务端支持多种口令加密算法**，客户端按服务端返回的能力协商（可能包括 RSA 与国密 SM2 两种）。

`ComposePanel::CheckPasswordEncryption` / `OnMenuMailPasswordEncryption` / `CoremailEngine::Mime::Compose::setPasswordEncryption` —— 写信时可以**给单封邮件加口令**（`LANG_*PASSWORDENCRYPTION*`），这是"加密邮件"的另一种模式：不依赖证书，靠共享口令。

## 6. 配置防篡改

`app/conf/privatization-setting.js` 是一个自校验的配置：

```json
{
    "ai_assist": true,
    "hash": "5a23728ef48054d31e5fab6af50dea82a1d017c13f1765cc65603bd1ce555480",
    "key": "public-version-air",
    "supported_protocol": "proprietary,imap,pop3,ews",
    "help_cnter": "https://help-cmc.coremail.cn/",
    "support_account": "cmcfeedback@coremail.cn",
    ...
}
```

对应文案：

```
LANG_SECURITY_SETTING_INVALID=安全配置文件已被篡改。
```

**推断**：`hash` 是文件内容的 SHA-256，启动时校验；校验失败会显示该警告，并可能降级某些功能（`enable_show_spell_check`、`enable_cmsm_certificate` 等开关可被回滚）。`key: "public-version-air"` 说明这是**"公有版-Air"**的配置集，同一个二进制可以通过不同的 conf 包变成不同产品形态（信创版、私有化版等）。

注意 `"hash"` 是 `5a2372...` 而二进制整体 sha256 是 `6f746f...`——两者无关，前者只覆盖这个配置文件。

## 7. 传输安全

| 项 | 事实 |
|---|---|
| ATS | `NSAllowsArbitraryLoads = true`（**不启用** ATS 保护） |
| 主机证书校验 | `is_check_cm_host_cert: true`（Coremail 自有开关，不是系统 ATS） |
| 私有协议传输 | **推断**为 HTTPS（接口是 `/s/json`），但 ATS 关闭意味着代码里可以随时降级到 http |
| IMAP/POP3/SMTP | 支持 `imaps` / `smtps` / 明文；预设里有明文项（见 `coremail/03` 第 7 节） |
| 证书库 | 内置根证书（`licensing/openssl` + 可能的私有 CA） |

**风险提示（观察层面的事实）**：
- `NSAllowsArbitraryLoads=true`；
- 内置预设含 `imap://imap.139.com`、`smtp://smtp-mail.outlook.com` 等明文条目；
- 这两点意味着**中间人攻击面比常规 macOS 应用更大**，实际是否被利用取决于用户手动配置。
