## 第一部分：IM 通信协议完整规格

### 1.1 传输层
- **协议**：WebSocket（默认 `ws://msg.bingolink.biz:10083`）
- **端点来源**：`localStorage.embWebSocketUri || config.embUrl`
- **数据帧**：二进制 `ArrayBuffer`（`binaryType` 默认）
- **协议版本**：`EMB_PROTOCOL_VERSION = 2.8`
- **客户端版本**：`Version: "5.1.9"`，`displayVersion: "5.2.97"`

> ⚠️ 注意：IM **不使用 Protobuf**。`google-protobuf` 依赖仅用于人脸识别 SDK。IM 是自定义二进制头 + JSON 负载协议。

### 1.2 二进制帧格式

#### 帧（客户端→服务端，编码函数 `C`）

```
┌────────┬────────┬────────┬────────┬──────────────────┬─────────────────────┐
│ header │command │ number │operation│  length (4 bytes)│  payload (UTF-8 JSON)│
│ 1 byte │ 1 byte │ 1 byte │ 1 byte  │   big-endian int │  length bytes        │
└────────┴────────┴────────┴────────┴──────────────────┴─────────────────────┘
```

| 字段 | 偏移 | 长度 | 默认 | 含义 |
|---|---|---|---|---|
| header | 0 | 1 | `5` | 协议头/版本标识 |
| command | 1 | 1 | — | 命令码（见 1.3） |
| number | 2 | 1 | `0` | 子标志位 |
| operation | 3 | 1 | `1` | 操作标志；`0` 表示无负载（如心跳） |
| length | 4..8 | 4 | — | payload 字节长度（大端） |
| payload | 8.. | length | — | UTF-8 编码的 JSON 字符串 |

> 解码端变量命名有混淆（decode 把 byte[2] 叫 operation、byte[3] 叫 number），但字节顺序与编码一致。

#### 帧解析（服务端→客户端）

```js
function parseFrame(bytes) {
  const t = {};
  t.header   = bytes[0];
  t.command  = bytes[1];
  t.operation= bytes[2];
  t.number   = bytes[3];
  if (!t.number) return t;                // number=0 无负载
  const len = (bytes[4]<<24) | (bytes[5]<<16) | (bytes[6]<<8) | bytes[7];
  t.length  = len;
  if (!len) return t;
  const jsonStr = new TextDecoder().decode(bytes.subarray(8, 8 + len));
  t.data = JSON.parse(jsonStr);
  // 非"发送消息回执"且含 content：解码 content
  if (t.command !== CMD.dSendMsg && t.data.content) {
    let s = decrypt(t.data.content);      // 见 1.5
    if (!isPlainTextMsg(t.data.msg_type)) s = JSON.parse(s);
    t.data.content = s;
  }
  return t;
}
```

### 1.5 内容"加密"算法（`k` 编码 / `I` 解码）

消息 `content` 字段在序列化为 JSON 前经过 **按位取反 + 自定义 Base64** 编码（伪加密，非真实加密）。

```js
// 编码 k(content)：UTF-8 字节 → 按位取反 → Base64
function encodeContent(str) {
  if (!str) return "";
  const bytes = Array.from(new TextEncoder().encode(str));
  for (let i = 0; i < bytes.length; i++) bytes[i] = ~bytes[i] & 0xff; // 按位取反
  return base64Encode(bytes);  // 自定义 Base64（字母表标准 A-Za-z0-9+/）
}

// 解码 I(content)：Base64 → 按位取反 → UTF-8 字符串
function decodeContent(b64) {
  if (!b64 || b64.length > 102400) return "";
  let bytes = base64Decode(b64);
  for (let i = 0; i < bytes.length; i++) bytes[i] = ~bytes[i] & 0xff;
  return new TextDecoder().decode(new Uint8Array(bytes));
}
```

> `content` 长度上限：102400 字符。`a.encrypt = k`，`a.decrypt = I` 暴露为模块 API。

### 1.6 客户端 API（IM SDK 模块 `a`）

```js
a.Init()              // 建立 WebSocket 连接，注册 onopen/onmessage/onclose/onerror
a.Auth(authPayload)   // 发送鉴权包（command=11, operation=1）
a.SendMsg(msgPayload) // 发送消息（command=3, operation=1）
a.SendMsgReceipt(p)   // 发送回执（command=13）
a.SendReadedMsg(p)    // 标记已读（command=14）
a.SendOfflineStart(p) // 启动离线拉取（command=102）
a.Beat()              // 发送心跳（command=6, operation=0, 无负载）
a.Beats(seconds)      // 启动定时心跳，间隔 = seconds 秒
a.ConfirmOnline()     // 重置心跳丢失计数（收到任意下行时调用）
a.Close()             // 关闭连接
a.Reconnet()          // 重连
a.getWebSocketState() // 返回 {state, desc}（0 CONNECTING / 1 OPEN / 2 CLOSING / 3 CLOSED）
a.encrypt = k         // content 编码
a.decrypt = I         // content 解码
```

#### 心跳机制
```js
// 启动定时器：每 (seconds*1000) ms 发一次 Beat
// 累计 3 次未收到回执（f>2）则 Close 重连
// 收到任意服务端包时调 ConfirmOnline() 重置计数
setInterval(() => {
  if (f > 2) { a.Close(); f = 0; }
  else { a.Beat(); f++; }
}, 1000 * seconds);
```

### 1.8.1 阅读回执（95 / 14 / 19）

- **逐条已读是普通消息 95（`uSendMsg=3`）**，不是会话级命令。content 形如：
  `{ readMsgIds: "<msg_id>[,<msg_id>…]", readMsgTypes: "<msg_type>", toId: "<会话 id>", toType: 1|2|4, sendToId: "<原消息发送人>", lastSendTime: <ms>, cmd: 1|2, clientReadTime: <ms> }`；
  `cmd=1` 阅后即焚删除、`cmd=2` 回执消息确认，普通已读不带 `cmd`。`readMsgIds` 可一次带多条——阅读者在同一时刻读了一批消息时只发一帧。
  外层信封的 `to_id/to_type` 指向**原消息发送人**（官方 `sendReadedMsg` 用 `sendToId/sendToType`），会话标识放在 content 的 `toId/toType`。
- **会话级 14 / 19 在官方桌面端是死代码**：`SendReadedMsg`（发送 command=14）只有定义、没有调用点；`onReadedSession`（14）与 `onReadedReceipt`（19）也没有订阅者。不要指望它们承载逐条回执。
- **官方在什么条件下发 95**：
  - 单聊消息 `is_need_send_read = 1`（`SEND_READTYPE.UNSEND`）：`getVisibleAreaReadedMsg` 在消息进入可视区时收集，再由 `sendReadedByMsgId` 发送；
  - 要求回执 / 阅后即焚的消息：打开阅读框时用 `sendReadedRecepit` 发送（`cmd=2/1`）；
  - **文件 / 云盘分享（3 / 14 / 30）**：开启自动下载时，可视区内的文件被自动下载，同时把 `msg_id` 加入待确认列表并发送 95——这是群聊里唯一会自然产生回执的消息类型；
  - 服务号消息另有 `RECEIPT(97)` 路径。
- **群聊文字不会产生回执**：`getDefaultSendReadType` 只对 `to_type = USER` 且非外部 `@` 账号返回 `UNSEND(1)`，群组/部门/工作群一律 `NONE(0)`；接收端 `is_need_send_read == 1` 的判定不成立，因此群聊文字没有人回 95。
- **显示规则**：官方只在自己的消息满足 `is_need_read_receipt || is_delete_after_read || (is_need_send_read != NONE && talk_with_type != GROUP)` 时显示已读状态。所以群聊普通文字在官方客户端不显示「已读/未读」，也不会出现「0 人已读」；复刻版按「真正收到确认才显示人数」处理。

### 1.8.2 发送端入口：回执消息 / 无痕消息（5.2.97 `home.js`）

官方不叫「阅后即焚」，也没有常驻复选框，而是输入框「更多」菜单里的两种**一次性模式**：

- 入口在工具条 `jdropmore` 菜单：单聊（`type=1`）显示「无痕消息」；群聊/部门（`type=2/4`）显示「回执消息」「回执卡片」。单聊本身已有逐条已读，所以不再提供回执消息。
- 选中后组件记 `floatingBarType`，输入框上方渲染 `FloatingBar`（白底、`#0093DD` 文字）显示 `[回执消息]`／`[无痕消息]`，右侧 × 取消。
- `prepareToSend` 先 `closeFloatingBar()` 再发送：模式只对下一条消息生效，发送后自动取消。
- 发送时 `is_need_read_receipt = floatingBarType ∈ {回执消息, 回执卡片}`，`is_delete_after_read = floatingBarType == 无痕消息`。
- 两者的区别只在正文标记：**回执消息**在 content 前置一个 U+200C，**回执卡片**不加。接收端在可视区扫描时，只有 `is_need_read_receipt && content.startsWith("‌") && !is_read_receipt_msg` 的消息会由 `readRecepitMsg` 自动回 95（`cmd=2`）；回执卡片要等接收人点开遮罩（`openMaskInfo`）才回执。回执成功后本地把 `is_read_receipt_msg` 置 1，遮罩消失。
- 模式激活时编辑器禁止插入截图，提示 `Msg_ReceiptNoContainPic「回执消息不能包含截图」`／`Msg_WuHenNoContainPic「无痕消息不能包含截图」`。
- 接收端：回执消息进入可视区自动回 95，回执卡片点开遮罩才回；无痕消息点开时发 95（`cmd=1`）。无痕弹窗 30 秒倒计时，关窗或到期销毁正文。

### 1.11 IM 复刻最小实现清单

1. **登录** → 拿 `AccessToken`、`CurrentUserId`、`DeviceId`
2. **建连** `new WebSocket('ws://msg.bingolink.biz:10083')`
3. **onopen** → 发 `Auth` 包（command=11）
4. **等 `dAuthDone`(200)** → 启动心跳 `Beats(30)`，发 `uOfflineStart`(102) 拉离线
5. **收 `dRecMsg`(3)** → 解码 content → 存库 → 通知 UI
6. **发消息** → 构造 payload → `k()` 编码 content → `C()` 组帧 → `ws.send()`
7. **收 `dBeats`(16)** → `ConfirmOnline()` 重置心跳计数
8. **重连** → 心跳 3 次丢失 `Close()` → `Init()` 重新鉴权

```
POST https://www.bingolink.biz/sso/oauth/token
  grant_type=password
```

返回：`access_token`、`refresh_token`、`expires_in`、`uid`、`identity`、`cipher_token`。

### 3.2 V2/V3 Token 互转

```js
// login_ticket 换 V3 token
POST {ssoEndpoint}/oauth2/jwt
  { access_token, alg:"rsa" }
// → jwt_token

// V2 access_token 换 V3
getV3AccessTokenByV2(v2_access_token, cb)

```

```http
LoginMode: manual
Authorization: Bearer <access_token>
```

## 第四部分：复刻建议与注意事项

### 4.1 推荐技术栈
- **壳**：Electron（与原版一致）或 Tauri
- **IM**：Node.js `ws` + 自实现二进制帧编解码（参考 1.2/1.5）
- **网盘**：HTTP 客户端直连 `pan.bingolink.biz/openapi`
- **存储**：SQLCipher（消息/会话本地加密）

### 4.2 复刻优先级
1. 登录鉴权（OAuth2 + RSA）
2. IM 连接 + 鉴权 + 心跳
3. IM 收发文本消息 + 离线拉取
4. IM 富消息（图片/文件，需与网盘联动）
5. 网盘文件列表/上传/下载
6. 网盘分享/权限/在线编辑

### 4.3 风险与未知项
- **服务端可达性**：`bingolink.biz`/`yuexiu.com` 为越秀受控服务，复刻后端如不可达需自建兼容服务（IM 服务端需实现命令码 3/6/11/13/16/97/101/102/200 等）
- **零信任网关**：`zt.yuexiu.com:443`（TrustAgent，AES key `75f242...`）可能介入部分请求，复刻时如不需可绕过
- **消息内容"加密"**仅为按位取反+Base64，非真实加密，复刻时可保留或替换为真加密
- **protobuf** 仅用于人脸识别 SDK，IM/网盘均不使用，无需引入
