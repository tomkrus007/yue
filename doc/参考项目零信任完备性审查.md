## 结论与判定标准

如果“完备”指独立替代官方零信任客户端，答案是否定的；如果指依赖已运行的官方代理，提供本地白名单分流，`kit` 已有可运行的基础实现。独立替代至少需要认证、设备/会话管理、可信策略获取与执行、官方隧道或等价网关通道，以及真实内网访问验证。不能把“本地代理开关开启”当作“零信任认证成功”。

## kit 尚存的具体缺口

1. **策略语义与说明不一致。** README 声称同一规则条件为“与”，实际代码是 `(byHost || byIp) && portMatches`，域名和 CIDR 是“或”；只有端口、没有域名或 CIDR 的规则永不命中。应先定义正确语义并补覆盖：[说明](/Users/tom/Downloads/yx-cloud-kb/repo/kit/README.md:72)、[实际判断](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/rules.js:114)。
2. **配置校验不足。** 正则直接 `new RegExp`，CIDR 掩码未限制 0～32，规则 action 未枚举校验；保存先写文件再编译，非法正则可留下无法使用的配置：[编译](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/rules.js:34)、[CIDR](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/rules.js:62)、[保存顺序](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/app.js:85)。
3. **热更新并非覆盖监听地址。** 更新只替换规则对象，监听 socket 不重绑；修改 `listen` 不会即时改变实际监听地址：[updateConfig](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/proxy.js:39)、[start](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/proxy.js:56)。
4. **开关不撤销已建立连接。** `setEnabled` 只改变之后的新连接决策，没有活动连接注册与断开操作；`stop()` 等待 server.close，也没有主动结束既有隧道：[开关](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/proxy.js:48)、[停止](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/proxy.js:93)。因此不能将其视为即时撤权。
5. **SOCKS5 协议处理尚不严格。** 入站直接选择无认证，没有检查客户端方法列表是否包含该方法；请求未检查 CMD，仅解析地址后建立 TCP 连接，未实现 UDP ASSOCIATE/BIND：[入站协商](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/proxy.js:279)。
6. **握手后的首批数据存在丢失风险。** HTTP/SOCKS5 上游握手读取缓冲后只返回 socket，没有将同批已读取的隧道数据恢复给后续消费者。这是源码可见的边界缺陷，当前测试未复现或覆盖：[HTTP 上游](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/upstream.js:30)、[SOCKS5 上游](/Users/tom/Downloads/yx-cloud-kb/repo/kit/src/zt/upstream.js:84)。

## Windows：手动链路已有记录，产品闭环仍未完成

Windows 部分比 kit 更进一步：原生组件实现代理入口、系统代理切换、TrustAgent 动态代理发现；另有登录脚本与脱离官方 IM 的操作流程。README 的“完整流程已验证”描述的是手动组合流程，不代表原生组件本身已集成全部认证生命周期：[直接登录说明](/Users/tom/Downloads/yx-cloud-kb/repo/win/README.md:128)、[手动完整流程](/Users/tom/Downloads/yx-cloud-kb/repo/win/README.md:168)。

- **按钮不等于零信任登录/退出。** 开启执行探测、启动本地代理、写系统代理；关闭禁用系统代理并停止本地代理，没有调用 TrustAgent 会话 login/logout。组件另有服务启停功能，应与会话认证区分：[main.cpp](/Users/tom/Downloads/yx-cloud-kb/repo/win/src/main.cpp:270)。登录、续期、失效重登、机器重启后的恢复与界面状态尚需形成统一流程。
- **上游自动发现不等于授权健康检查。** 自动发现失败会将请求退回直连：[zt.cpp](/Users/tom/Downloads/yx-cloud-kb/repo/win/src/zt.cpp:467)。TrustAgent 端口探测失败还会尝试其他进程的候选端口；探针检查公网百度 80 端口，不能证明内网访问或当前身份授权有效：[探针](/Users/tom/Downloads/yx-cloud-kb/repo/win/src/zt.cpp:909)、[候选回退](/Users/tom/Downloads/yx-cloud-kb/repo/win/src/zt.cpp:999)。这符合保持联网的设计，却不能作为隧道在线的判断。
- **“关闭恢复原代理”未兑现。** 开启直接覆盖 ProxyServer/ProxyEnable，关闭只是把 ProxyEnable 设为 0，没有保存恢复用户原有代理设置：[系统代理实现](/Users/tom/Downloads/yx-cloud-kb/repo/win/src/zt.cpp:1036)。
- **真实原生组件验收缺失。** README 明确 Windows 实际运行、系统代理写入和代理转发行为未验证；不能用交叉编译与纯规则单测替代 Windows 端到端验收：[构建验证说明](/Users/tom/Downloads/yx-cloud-kb/repo/win/README.md:60)。本轮仅在本机执行了 Windows 规则引擎 C++ 单测，全部通过，未运行 Windows 程序。
- **文档存在不同步。** README 前文说默认自动发现，末尾仍说默认直连；知识库中“自动发现待办”的旧说明也不能代表当前实现：[当前默认说明](/Users/tom/Downloads/yx-cloud-kb/repo/win/README.md:30)、[旧说明](/Users/tom/Downloads/yx-cloud-kb/repo/win/README.md:204)。

## 建议验收顺序

1. **优先明确产品边界。** 推荐先按“保留 TrustAgent、替代官方 IM 并复用其代理”验收；独立隧道不是当前实现能力。
2. **补齐认证和状态闭环。** 集成登录、续期、失效处理、重启恢复；状态至少区分本地代理监听、官方会话有效、内网资源可达。用用户授权的真实内网目标做健康检查，避免公网通就显示零信任在线。
3. **修复系统代理恢复。** 启动前保存原配置，正常关闭恢复，并明确异常退出后的恢复路径。
4. **完成 Windows 端到端验证。** 从干净启动到认证、自动发现、命中规则访问内网、未命中直连、登出/失效、重启恢复均应有可重复记录。已有历史人工探测不能替代该验收。
5. **完善分流器边界。** 修正规则语义、配置校验、异常协议和连接生命周期，并补普通 HTTP、SOCKS5 上游、失败路径与首包数据的本地集成覆盖。

若目标是完全脱离 TrustAgent，则还需完成网关认证、设备态、策略同步及隧道协议研究，现有实现不能直接作为成品交付。
