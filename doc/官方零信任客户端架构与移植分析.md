# 官方零信任客户端（TrustAgentLauncher）架构与移植分析

分析日期：2026-11-06。对象：`/Applications/TrustAgentLauncher.app`（奇安信零信任客户端，`CFBundleShortVersionString = 3.3.0`，内部源码树 `ztna_client_3302` / `ztna_client_hotfix_3.3.2`，构建目录名含 `ac-trustagentlauncher_dev_yuexiu`，即越秀 OEM 分支）。

**证据等级说明**：本次只用 REA 的 macOS 静态能力（bundle 清单、`Info.plist`、代码签名权限、Mach-O 符号表、字符串表）分析，未运行客户端、未登录、未访问网关，也未使用真实账号。当前 REA 会话只挂了 `native-macos` 与 `rea-artifact-graph` 两个 provider，没有 Ghidra/IDA，因此**没有反编译体**，所有结论来自符号名、格式字符串与资源清单；凡是推断都会标注。客户端本地数据文件（`TrustAgentCredential.db`、`topic_register.db`、`utilsfiledb`）是加密的，`sqlite3` 打不开（`file is not a database`），无法据此还原配置结构。

---

## 1. 结论摘要

1. 官方客户端不是"本地白名单代理"，而是**完整的分层零信任端点**：控制面（REST 会话/策略）+ 数据面（DNS 劫持 → 虚拟 IP 路由 → TUN → tun2socks → 按 `svcid` 逐连接鉴权 → 私有隧道到网关）。
2. 真正不可替代的部分只有一个：**网关隧道协议**（TLS 之上的私有二进制帧 + `svcid` 连接重定向）。其余都可以在本机用标准接口复现。
3. 对 `YX` 来说，**不需要移植整条链路**。客户端已经提供了标准的本地 HTTP 代理 + PAC，`YX` 现有的 `src-tauri/src/zt.rs` 只要把 upstream 指向它即可；再往上一档可以做"控制面移植"（登录/会话/应用列表/免登票据），**不建议**做全隧道重写。
4. 平台限制是硬约束：系统级 DNS 劫持依赖 `com.apple.developer.networking.networkextension`（`dns-proxy-systemextension`）和系统扩展安装权限，普通 Tauri 应用拿不到（见第 5 节的签名权限证据）。

## 4. 数据面：流量到底怎么走

由 `TrustService.framework` 的符号与日志可还原出下面这条链（符号名为直接证据，箭头关系为推断）：

```
应用/浏览器
   │  (1) DNS 查询
   ▼
[NEDNSProxyProvider / trustdns 系统扩展]  ── 命中策略的域名 ──► 返回 mock IP
   │                                                   （`[wildcard_domain] mockip=%s`）
   │  (2) TCP 连到 mock IP
   ▼
utun（trustvnic）+ 路由：route_includes4/6、route_excludes4/6、route_assign4/6
   ▼
tun2socks（go-tun2socks v1.16.11 / lwip）→ 本地 SOCKS5
   ▼
TrustTunnelConnection（TLS 到网关，SNI、可选双向证书、可选国密）
   │  (3) PRD_PROXY_AUTH / svcid 鉴权
   ▼
网关按 svcid 把连接还原成真实目标，双向转发
```

关键证据与语义：

- **`svcid` 是按连接粒度做授权的最小单位**：
  `Query service id by hostname returns: dst=%s_%d, ip=%s, svcid=%d`、
  `svcid=0(bypass)`、`svcid=0xFFFFFFFF(Blocking)`、
  `[proxytun] received the PRD_PROXY_AUTH response: svcid=%d, errcode=0x%08x`、
  `Redirect connection: svcid=%d, src_addr=%s_%d, dst_addr=%s_%d`。
  即：本地维护"目标 → svcid"表，`0` 直连、`0xFFFFFFFF` 拦截、其余走隧道并要求网关授权。
- **TLS 层参数可配**：`vpn_sni`、`ssl_twoway`、`ssl_smx`（国密）、`sm4_ecb_optimized`、`ssl_fingerprint_put`/`sp_ssl_fingerprint_check`（证书指纹固定）。日志：`Connecting to vpn[%s_%d]: ssl_sni=%s, ssl_twoway=%d, ssl_smx=%d`。
- **隧道是私有二进制帧**：`tag=0x%08x plen=%ld mlen=%ld, dlen=%ld, result=0x%08X`、`read handshake reply: tag=0x%08X, mlen=%d`、`Received the message response: mtag=0x%08X`。即 4 个长度字段 + tag + result 的自定义信封，不是 HTTP/2、不是 gRPC；另有 `SPWSClient::Handshake`（WebSocket 备用通道）与 `SPCmdParser::JsonRpc`（本地命令通道）。
- **DNS 策略由服务端下发**：`trust_session_set_dns_policy`、`[trustdns] dns policy json:%.1024s`、`wildcard_domain` / `wildcard_domain_excludes`、`dns_gateway`（可由网关代答 DNS）。
- **路由策略由服务端下发**：`ParseSessionUTUNPolicy`、`utun_ipv4/utun_ipv6`、`need_build_utun`/`needUTUN`、`route_opt`/`route_auto`。
- **模式可选**：`TUNNEL_ALGO`（`AppCfg::GetTunnelSetting`）、`sigL4ProxyLoaded`、`IPSec Tunnel`；说明产品本身支持"L4 代理"（仅应用层代理，不起 TUN）与"UTUN/IPSec"多种形态，不是单一实现。

## 5. 本地接口：可直接被第三方复用的部分

| 接口 | 位置 | 说明 |
|---|---|---|
| PAC | `http://127.0.0.1:<port>/get_trust_pac?proxy_server=<host>:<port>` | 模板在 `TrustService` 里：`function FindProxyForURL(url, host)`、`var BLOCKED = 'PROXY 127.0.0.1:10'`；另有 `http://127.0.0.1:<port>/get_pac` |
| 本地 HTTP 代理 | 同 PAC 中 `proxy_server` 指向的端口 | Go `net/http` 实现，支持 `CONNECT`（字符串表含 `CONNECT`、`Proxy-Authorization`）与 `/_proxy/<...>` 路径；`/_tool/nslookup` 提供诊断 |
| 系统代理写入 | `SCDynamicStore` + `ProxyAutoConfigEnable` / `ProxyAutoConfigURLString` | 客户端自己把 macOS 系统代理切成 PAC 模式（推断，来自符号与 PAC 模板） |
| 引擎命令通道 | `http://127.0.0.1:<port>/zerotrust/trustsdk`、`/zerotrust/sse_message`、`/get_token` | JWT 保护的 JSON-RPC；命令名可见：`sac_auth`、`sac_auth_sub`、`sac_app_list`、`sac_get_portal`、`sac_get_userdata`、`sac_heartbeat`、`sac_logout`、`secid_login`、`SessionSetVpn`、`SessionSetTunnel`、`GetPAC` 等（`SPCmdParser`） |
| 状态查询 | `http://127.0.0.1:36440/zerotrust/trustcore`、`http://127.0.0.1:39300/zerotrust/trustenv`、`/ping` | 端口在 `36440–36443`、`39300–39303` 区间内探测（`GetTrustCoreLiseningPortRange`、`probeTrustCoreListeningPort`、`trustagentservice` 的 `update_turstcore_port`） |
| 设备指纹 | `http://127.0.0.1:<port>/_zerotrust/agent?method=get_mid&challenge=<...>&version=v2&encode=none`（HTTPS 变体同路径） | 返回机器码 mid（硬件序列号派生，`zt_get_mid.cpp`），`trustdservice` 每 300 s 刷新；`tripledes.go` 说明响应可 3DES 加密 |
| 合规采集 | `http://127.0.0.1:39440/service_mgr/{ping,query,command,launch,wait_event}` | osquery 派生表（进程、防火墙、屏幕锁、共享设置等） |
| 单实例/IPC | `/tmp/ztrust_socket`、`/tmp/ztrust_plugin_socket` | `QAppLocalServer`（`Init(QString const&)` + `slotNewConnection`）与 `QAppLocalClient::SendActiveMessage`；推断为本地 socket 监听，具体 Qt 类名未在符号表出现 |

**平台权限**（`codesign -d --entitlements`）：

- 容器 App：`com.apple.developer.networking.networkextension = [dns-proxy-systemextension]`、`com.apple.developer.system-extension.install = true`、`application-groups`。
- 这意味着 DNS 劫持不是"改 /etc/hosts"，而是 Apple 审核过的 NetworkExtension 能力。**普通签名/自签应用拿不到**，所以系统级 DNS 分流无法在 `YX` 内复刻。

## 6. 移植可行性矩阵

| 能力 | 能否移植 | 说明 |
|---|---|---|
| 本地 HTTP/CONNECT 代理 + 规则分流 | ✅ 已有 | `YX/src-tauri/src/zt.rs` 已实现，且 `upstream` 支持 `http`/`socks5` |
| 系统代理/PAC 切换 | ⚠️ 需提权 | 写 `SCDynamicStore` 或 `networksetup -setautoproxyurl` 要管理员授权；必须做"原配置备份/异常恢复"，参考项目在这一块有已知缺陷 |
| 控制面登录/会话/应用列表/免登票据 | ✅ 可行 | 纯 HTTPS+JSON，接口清单见第 3 节；需要可用的网关地址与账号 |
| 服务端下发的"目标→是否代理"策略 | ✅ 可行 | `terminalPolicy/detail`、`init_session` 返回的 DNS/代理规则可直接映射到 `zt.rs` 的 `rules` |
| UTUN + tun2socks + 虚拟 IP | ❌ 不建议 | 需要 utun 权限与路由接管；`YX` 只访问固定 HTTPS 域名，收益远小于风险 |
| 系统级 DNS 劫持 | ❌ 不可行 | 需 NetworkExtension + 系统扩展签名（见第 5 节） |
| 网关隧道协议 | ❌ 本轮不可行 | 私有二进制帧 + `svcid` + 可选国密；无反编译器、无运行时捕获、无测试账号，且属于产品核心协议 |
| 合规采集（osquery 表） | ❌ 不需要 | 与业务无关，且采集面很宽，移植会带来隐私与合规风险 |
| HTTPS 中间人（客户端内有 `tlsListener` + `rootCA.pem`） | ❌ 不建议 | `Resources/rootCA.pem` 是 mkcert 开发证书（subject `mkcert development CA`），当前构建未见安装到系统钥匙串；做中间人会破坏证书固定并放大风险 |

## 7. 三条可落地路线

### 路线 A（推荐，1–2 天）：把官方客户端当隧道引擎，`YX` 只做"发现 + 分流"

已实现（`YX/src-tauri/src/zt.rs` 的 `upstream.type = "auto"`）：

1. 先读系统代理（`scutil --proxy`）：官方客户端接管时 `ProxyAutoConfigURLString` 形如 `http://127.0.0.1:<port>/get_trust_pac?proxy_server=127.0.0.1:<proxy>`，直接取 `proxy_server`；没带参数就取该 PAC 内容解析 `PROXY host:port`。
2. 系统代理没被接管时，退化为探测引擎候选端口 `36440–36443` / `39300–39303` 的 `GET /get_pac`，从 PAC 内容里解析代理地址。
3. 结果缓存 30 s，探测失败回落直连（不阻断业务）；状态里只暴露"实际使用的上游"，不伪造在线状态。
4. `rules` 用"内网域名后缀 → proxy，其余 direct"。UI 只展示"监听地址 / 上游 / 命中日志"，不做伪"登录成功"状态。

优点：零协议风险，走官方鉴权与审计；缺点：依赖官方客户端在运行。

这本质上是把现有 `kit/src/zt` 的"人工填上游"改成"自动发现上游"，补齐参考项目里最大的可用性缺口。

### 路线 B（2–4 周）：移植控制面，用服务端策略驱动本地分流

1. Rust 侧实现 `pre_auth → login → init_session → terminalPolicy/detail`，拿到 token、会话、DNS/代理规则。
2. 规则映射：命中 `wildcard_domain`/`proxy_rules` 的走 `proxy`，`svcid=0xFFFFFFFF` 映射成 `block`，其余 `direct`。
3. 有了 token 后还能实现"应用列表 + 免登票据"（`authz/applications`、`authz/authorize`），把 `YX` 从"复刻聊天"扩到"应用门户"。
4. 前置条件：必须有真实网关地址与测试账号；`api/v2/*` 的请求体字段尚未从二进制中还原（本轮无反编译器），需要抓一次真实登录流量确认字段名。

### 路线 C（不建议，> 1 人月）：重写隧道

必须完成：`TrustTunnelConnection::handshake` 的 tag/长度语义、`PRD_PROXY_AUTH` 的 `svcid` 鉴权报文、TLS 层参数（SNI / 双向证书 / 国密 SM2-SM4 / 指纹固定）、帧多路复用与保活。
需要先补条件：REA 挂上 Ghidra provider；用 Frida/LLDB 在 `SSL_write`/`SSL_read` 上抓一次真实会话（客户端未登录、无账号时无法进行）；拿到网关测试环境。即使全部完成，也仍有合规风险。

## 8. 已落地的改动（路线 A 最小版）

1. `src-tauri/src/zt.rs`
   - `UpstreamConfig.type` 增加 `auto`；`resolve_upstream()` 在连接时把 auto 解析成具体 HTTP 上游，解析失败回落 `direct`。
   - `probe_system_proxy()`：读 `scutil --proxy`，从 `ProxyAutoConfigURLString` 的 `proxy_server` 参数取地址，必要时再取 PAC 内容解析 `PROXY`。
   - `probe_pac()`：候选端口 `36440–36443` / `39300–39303` 的 `GET /get_pac`。
   - 结果缓存 30 s（含"没找到"的负结果）；`zt_start` 时后台探测一次，避免拖慢启动。
   - `ZtStatus` 新增 `upstream: { host, port, source } | null`；状态查询只读缓存，不触发探测（UI 每 2 s 轮询一次）。

## 10. 能否把 TrustAgent 提取出来集成进 `YX`

结论：**按"从 `.app` 里拷组件、自己签名、塞进 `YX` 分发"这条路走不通**，不是工作量问题，是三道签名/权限门槛。真正的"独立于 `/Applications/TrustAgentLauncher.app`"只有三条路：厂商 SDK、用户级代理自实现、网关侧改造。

### 10.1 三道硬阻断（有证据）

1. **提权 helper 只认厂商客户端**
   `Contents/Library/LaunchServices/com.legendsec.jobblesshelper` 的内嵌 `Info.plist`：
   `SMAuthorizedClients = identifier "com.legendsec.trustagentlauncher" and anchor apple generic and ... certificate leaf[subject.OU] = "2D47J675T6"`。
   也就是只有 bundle id 为 `com.legendsec.trustagentlauncher`、且由厂商 Team `2D47J675T6` 签名的调用者才能 bless 这个 helper。`YX` 无论怎么签名都不满足，改 helper 的 plist 会直接破坏它自己的签名。
2. **系统扩展必须由厂商容器 App 安装**
   `dnsproxy.systemextension` 的权限是 `2D47J675T6.com.legendsec.trustagentlauncher.dnsproxy` + `com.apple.developer.networking.networkextension = [dns-proxy-systemextension]` + app group `2D47J675T6.com.legendsec.trustagentlauncher`，且带厂商 provisioning profile。`OSSystemExtensionRequest` 只能激活**本 App 内、与本 App 同签名主体**的扩展；`YX` 无法安装、也无法复用别人的扩展。
3. **root 能力全在 vendor 侧**
   Swift 容器里可见完整清单：`/Library/PrivilegedHelperTools/%@`、`/Library/LaunchDaemons/%@.plist`、`sudo launchctl unload -wF`、`security add-trusted-cert -d -k /Library/Keychains/System.keychain %@`、`OSSystemExtensionRequest activation/deactivation`。utun（`PlugIns/trustvnic`）、本地代理守护进程（`trustagentservice`/`trustagentsdk`）都是 root LaunchDaemon。

补充证据：所有二进制均为 hardened runtime（`flags=0x10000(runtime)`、Team `2D47J675T6`），注入/替换 dylib 也会被库校验拦；`trustagentservice` 里硬编码 `/Applications/TrustAgentLauncher.app/Contents/Info.plist` 并用 `ps aux | grep TrustAgentLauncher` 判断存活，搬走路径后自身逻辑就会失配；`TrustAgent.app`（Qt）没有任何 entitlements、也没有链接 `TrustService`/`TrustNetwork`，它只是 UI——**隧道宿主是 Swift 容器进程**，把它单独拷出来没有任何隧道能力。

### 10.2 三条可行路线（按推荐度）

| 路线 | 做法 | 前置条件 | 风险 |
|---|---|---|---|
| ① 厂商 SDK / 定制 | 向奇安信（或越秀 IT）要可嵌入的客户端 SDK、无界面代理，或让厂商重新签名一个精简容器 | 商务/采购沟通；确认是否支持第三方宿主 | 低（唯一可持续方案） |
| ② 用户级 L4 代理自实现 | 只复刻"认证 + 本地代理 + TLS 隧道"，不做 TUN/DNS/系统扩展 | 需协议逆向（见路线 C）+ 网关测试环境 | 中高（工作量大、协议可能变更、条款风险） |
| ③ 网关侧改造 | 由 IT 在网关/应用前置层提供 Web 反向代理或 API 网关，`YX` 用普通 HTTPS 访问 | 需服务端配合 | 低（但要改服务端） |

关键判断：**TUN、DNS 劫持、开机自启、证书安装这些"系统级"能力无法搬，但"本地 HTTP 代理 + TLS 隧道"本身不需要 root**——所以如果只是让 `YX` 自己访问内网 HTTPS 服务，②在权限上是成立的，卡点只在协议。

### 10.3 如果"独立"只是"不打开官方界面"

那不需要提取任何组件：第 7/8 节的 `auto` 探测已经能在官方客户端以守护进程运行时完成对接。可以再加一步"未发现上游时提示并引导启动官方客户端"，用户侧同样看不到 `TrustAgentLauncher` 的界面。

### 10.4 不建议做的事

- 直接拷贝/重签名厂商二进制并随 `YX` 分发：几乎必然违反许可协议，且第 10.1 的三道校验会让它跑不起来，属于"高成本 + 不能用"。
- 把 `TrustAgent.app` 作为嵌套 App 塞进 `YX` 再 `open`：仍然是运行厂商整套组件（含 root 安装、系统扩展），既没有摆脱依赖，又把签名链搞复杂。

## 12. 协议逆向进展（2026-11-06 第二轮，纯静态）

### 12.1 方法

- 目标：`Contents/Frameworks/TrustService.framework` 的 **arm64 切片**（C++，带完整符号），必要时用 Android `libzerotrust.so` 交叉验证。
- 工具：`nm -a`（符号表）、`otool -arch arm64 -tV -p <mangled>`（按符号反汇编）、`otool -l/-s`（段与常量）、自写 `re_xref.py`（扫 `otool -tV` 输出，靠 `; literal pool for: "..."` 注释把字符串引用落到函数名）。
- 注意：fat 二进制里 `otool` 给的 file offset 是**切片内偏移**，直接按它读原文件会错位；读常量要用 `otool -s` 或加上切片偏移。

### 12.2 已确认：本地代理的 Basic 认证口令是可推导的（无需任何密钥）

`SPSession::SPProxyAuthGenerateTrustPasswd(std::string seed, int window)` @ `0x1d1f40` → `SPSession::GeneratePasscode(const char*, size_t, int)` @ `0x1d3ac8`：

```
seed16 = seed 的前 16 字节，不足则循环取（模 strlen）
slot   = floor(now_ms / 1000 / 60) + window    // 分钟槽；window 为 ±1 的容错偏移
key    = BE64(slot)                            // rev x8 后按大端写入 8 字节
mac    = HMAC-SHA1(key, seed16)                // SPCrypto::HMACHash(..., "SHA1")
off    = mac[19] & 0x0f
v      = BE32(mac[off..off+4]) & 0x7f7fffff
code   = sprintf("%06u", v % 1000000)
```

证据（`otool -p` + 逐字节解码）：
- `lsr x8,x0,#3`、`movz/movk` 组 `0x20C49BA5E353F7CF`、`umulh`、`lsr #4` —— 已用 Python 对 `t` 全域验证等价于 `/1000`（取秒）。
- 随后 `add x8, x8, 60*window`、`mov x9,#0x8888888888888889`（`orr`+`movk #0x8889`）、`umulh`、`lsr #5` —— 等价于 `/60`（取分钟）；两处除法都已验证**精确**（非近似）。
- `rev x8` 是转大端后写入 8 字节 key；`and w8,w8,#0xffffff7f` + `rev` 是标准动态截断；`snprintf(buf,16,"%%0%du",6)` 输出 6 位补零。

调用点（`re_xref.py` 定位）：

| 调用者 | seed | 含义 |
|---|---|---|
| `SPSession::CheckValidityOfUsernamePassword(user, pass, ctx)` @ `0x1d37f8` | `user` | **本地代理校验入站 Basic 口令**：pass 必须等于 `HOTP(user)` |
| `SPToolsModule::ExecQueryConnectStatus` @ `0x308cac` | 常量 `"trustagent"` | 自检：`CONNECT` 到 `127.0.0.1:<本地端口>`，用户固定 `trustagent` |
| `SPToolsModule::ExecHttpRequestTask` | 运行期字符串 | 工具类 HTTP 请求 |

`SPNetSocketTCP::ProxyConnect` @ `0x2a5e44` 直接拼：
`CONNECT %s%s:%d HTTP/1.1\r\nProxy-Authorization: Basic %s\r\n\r\n`（口令 `SPString::Base64Encode`）。

**推论（重要）**：这个 Basic 认证是**本机防滥用**，不是网关认证——因为唯一调用者连的是 `127.0.0.1`、用户固定。也就是说，本机任何程序只要知道用户名就能算出正确口令，属于设计缺陷；对我们则意味着"本地代理层"零成本可复刻。

### 12.3 已确认：PAC 与本地端口

`SPSession::BuildPAC` @ `0x1d4e20` 的模板常量：

```
var DIRECT       = 'DIRECT';
var SP_PROXY     = 'PROXY %SP_PROXY_ADDR%; SOCKS %SP_PROXY_ADDR%; SOCKS5 %SP_PROXY_ADDR%;';
var BLOCKED      = 'PROXY 127.0.0.1:10';
var DIRECT_LIST / PROXY_LIST / EXCLUDE_LIST / BLOCKED_LIST
```
其中 `%SP_PROXY_ADDR%` 由 `snprintf(buf, "127.0.0.1:%d", 本地端口)` 填入。即**分流仍然回指本机**，由本机 hub 代理再进隧道；`BLOCKED` 用 `127.0.0.1:10` 占位。这也解释了为什么 `YX` 只要拿到本机端口就能复用。

### 12.4 已确认：`PRD_PROXY_AUTH` 报文布局（`SPSession::BuildServiceProxyAuthMsg` @ `0x1d7c40`）

按写入顺序（多数字段是 **大端 u32 长度 + 值 + 4 字节对齐补齐**）：

## 13. 隧道帧格式与 L4 握手（2026-11-06 第三轮）

### 13.1 两个隧道要分清

| 隧道 | 实现 | 承载 | 用途 |
|---|---|---|---|
| NC 隧道 | `TrustTunnelConnection`（TrustService） | 原始 IP 包（L3） | UTUN 模式，`TrustPacketTunnelProvider` + lwIP |
| L4 隧道 | `SPTapTrustTunnelTCP`（SP 引擎） | 按连接的重定向 + JSON-RPC | **本地代理模式（我们需要的）** |

`YX` 只需要 L4：本地跑一个 HTTP 代理，每个 CONNECT 向网关发一次 `authz`，成功后双向转发字节。

### 13.2 NC 隧道（L3）帧 —— 顺带确认了整型布局

`TrustTunnelConnection::handleSocketReadData`（`0x51784`）：

```
while (len > 8):
    mlen   = BE32(buf[0..4])          // rev w27,w9；getIntFromData 就是 ldr+rev
    if (len-4 < mlen) break           // 半包，等下次
    ver    = buf[4]                   // 只接受 4 或 6（IPv4/IPv6）
    payload= buf[8 .. 8+mlen-4)       // 原始 IP 包
    len   -= mlen+4                   // 整帧 = 4 + mlen
    mlen > 0x57c(1404) → TrustIpPacketFragment 分片
```
`SetProtocol`：`ver==6 ? 30(AF_INET6) : 2(AF_INET)`。

握手（`TrustTunnelConnection::requestNCAuthorization`，`0x529f4`）：

```
magic = "PTUN"           // mov w8,#0x5450; movk #0x4e55 → 内存字节 50 54 55 4E
send("PTUN" + BE32(json_len) + json)
json = {"local_subnet": "<子网用 | 连接>"}     // TrustGetSubnet::GetLocalSubnet
reply: recv(4) → BE32 datalen; recv(datalen) → JSON
```

### 13.3 L4 隧道（`SPTapTrustTunnelTCP`）：JSON-RPC 2.0

`OnHandshakeReq`（`0x3585e8`）构造并发送的请求体（字面量顺序即写入顺序）：

```json
{
  "jsonrpc": "2.0",
  "method": "authz",
  "lang": "<语言>",
  "seq": "<SPString::RandomString>",
  "params": {
    "app": {
      "process_name": "...",
      "os": "...",
      "signature": "...",
      "process_path": "...",
      "process_hash": "<64 hex>",
      "product_name": "...",
      "file_version": "<64>"
    },
    "app_uuid": "...",
    "dst_host": "...",
    "dst_port": "<十进制字符串>",       // SPString::LToA(len 10)
    "schema": "appdetect",
    "identification": "...",
    "user_app_info": { ... }            // 仅当 SPTrustScheduleMsgHandler::TrustAccessEnabled()
  },
  "access_token": "<会话 token>"
}
```

封包（`0x35940c`–`0x3594a8`，`ctx->0x50` 为写缓冲区）：

```
u32 BE tag  = 0x11000001        // 8 字节常量 11 00 00 01 00 00 00 00，后 4 字节会被覆盖
u32 BE plen = total_len - 8
u32 BE dlen = json_len
json bytes（4 字节对齐补齐）
```
这与日志常量 `tag=0x%08x plen=%ld mlen=%ld, dlen=%ld, result=0x%08X` 完全对应；`BuildServiceProxyAuthMsg` 里出现的另两个 8 字节常量 `01 00 00 01`、`03 00 00 11` 应为同族的其它 tag（`0x01000001` / `0x03000011`，用途待定，推测为代理鉴权与数据）。

**含义**：L4 模式对网关就是"一条 TLS 连接 + 若干 JSON-RPC 请求 + 之后按连接转发"；`dst_host/dst_port` 就是我们想访问的内网目标，`access_token` 来自登录会话。这与之前从 PAC/日志推断的 `svcid` 模型并不矛盾——`svcid` 是策略侧的"该目标属于哪个服务"，而 L4 authz 用 `dst_host/dst_port` 直接问网关。

### 13.4 由此得到的"最小可跑通"实现路径

1. 登录拿到 `access_token`（REST，见第 3 节；字段名待第 14 节补）。
2. 与网关建立 TLS（SNI = `vpn_sni`，可选双向证书/国密；先用普通 TLS + 系统信任链试）。
3. 对每个目标发 `tag=0x11000001` 的 `authz` 请求（`os` 随手填 `macos`，`signature`/`process_*` 可为空串，`schema=appdetect`）。
4. 解析回复（`OnHandshakeRsp`，下一步要反）→ 成功后按数据帧 tag 转发。

### 13.5 尚未确认（下一步）

1. `authz` 回复的 JSON 结构与错误码（`OnHandshakeRsp` @ `0x356a98`）。
2. 数据帧 tag 与分片规则（`OnTapVpnRead`、`WriteAppRsp`）。
3. `access_token` 的获取与续期请求体（Qt 侧 `TrustReq::Format*`）。
4. `seq`/`identification` 的取值约束（是否参与签名校验）。

风险：以上都是静态推断，tag 数值与字段名需要一次真机会话来验证；若网关侧校验 `app_hash`/`signature`，需要按真实进程信息填。

## 14. L4 隧道协议闭环 + Rust 实现（2026-11-07）

### 14.1 应答侧：握手回复就是一帧 JSON

`SPTapTrustTunnelTCP::OnTapVpnRead`（`0x356784`）：

```
mode = ctx->[1]
mode == 7 → 直接丢弃（错误/关闭态）
mode == 6 → 原始转发：vpn_input 直接 add 到 app_output（握手之后的字节管道）
否则（握手态）：
   need >= 9 字节 → pullup(8)
   plen  = BE32(hdr[4])          // 整帧 = plen + 8
   total > 已有长度 → 继续等
   读出 tag(BE32 at 0) / dlen(BE32 at 8) / json
   日志：`read handshake reply: tag=0x%08X, mlen=%d`
   → OnHandshakeRsp(json)
```

`OnHandshakeRsp`（`0x356a98`）解析：

| 字段 | 含义 |
|---|---|
| `error.code` / `error.message` | JSON-RPC 错误，非 0 即失败（默认 message 为 `tunnel error`） |
| `status_code` | `401` → **立即登出**（日志 `received status_code 401, Logout now.`）；非 0 视为失败 |
| `data` | 附加数据（含 `svcid` 等） |
| `bRetAppDetectAuthz` / `strRetAppDetectAuthzFail` | 应用识别结果，用于通知 `trust_appdetect_authz` |

**结论：握手成功后没有额外分帧，连接退化成原始 TCP 字节流。** 这一点是整条链最关键的简化——我们不需要复刻 `svcid` 的数据帧。

### 14.2 已实现：`YX/src-tauri/src/zt_tunnel.rs`

| 能力 | 对应逆向结论 |
|---|---|
| `encode_json_frame(tag, json)` | `tag(4) \| plen(4) \| dlen(4) \| json \| pad4`，plen = 总长-8 |
| `read_frame(r)` | 与 `OnTapVpnRead` 相同：先读 8 字节、按 plen 读满、再取 dlen |
| `build_authz_request(ctx)` | JSON-RPC `method=authz`，`params.app.*` / `dst_host` / `dst_port`(字符串) / `schema=appdetect` / `access_token` |
| `check_authz_reply(tag, json)` | `error.code`、`status_code`、401 分支 |
| `connect_tls(...)` | rustls（ring provider）+ 可选严格校验；SNI 可配 |
| `open(gateway, port, opts, ctx)` | TLS → authz → 返回可读写的隧道流 |
| `zt_tunnel_probe`（Tauri 命令） | 诊断：只握手不转发，返回 TLS 版本/加密套件/耗时 |

Tauri 命令签名（前端 `ztTunnelProbe`）：

```ts

```

## 15. 控制面也是 JSON-RPC（2026-11-07）

之前第 3 节记的是"REST 路径"，实际请求封装是 **JSON-RPC 2.0**；`api/v2/...` 那批是网关的 Web/REST 侧，
客户端自己走的是下面这套（`TrustReq::*`，在 Qt 二进制里）：

| 构造器 | 报文 |
|---|---|
| `TrustReq::FormatRequestJson(method, params)` | `{"jsonrpc":"2.0","id":N,"method":<method>,"params":{...}}`；`method` 为空时默认 `trust_session_request`，可带 `action` |
| `TrustReq::FormatPreAuth(_PREAUTH_INFO, bool)` | `method = "trust_pre_auth"`，字段：`instanceId` `type` `username` `password` |
| `TrustReq::FormatTrustHttpRequest(url, params, timeout)` | `method = "trust_tools_http_request"`，字段：`url` `timeout` `params` |
| `TrustReq::FormatAuthRequest(_AUTH_INFO, int)` | 按场景分三种 method（见下） |

`FormatAuthRequest` 的字面量集合按分支切分：

| method | 关键字段 |
|---|---|
| `trust_session_login` | `auth_factor`（`USER_PWD` / `SMS`）、`instanceId`、`uiType`、`score`、`tac_host`、`tac_port`、`trust_ip_fixed`、`isSecondaryAuth` |
| `trust_session_request` | `action`、`check_mfa`、`session_id` |
| `trust_manage_device` | `action = "unbind_device"`、`user_uuid`、`dev_uuid` |

Web 单点登录分支另拼 `https://<host>:<port>/runtime<path>`（`QAuthWebForm::slotHandleResult`，`0x100086a9c`）。

**对移植的意义**：登录与隧道是同一套信封，`access_token` 由 `trust_session_login` 返回，
之后既可用于隧道 `authz`，也可用于 `trust_session_request` 拉策略。也就是说，
第 14 节的隧道实现只差一个 token 就能对接真实网关；token 的取得需要一次真实登录（账号或 SSO）。

### 18.3 TLS 模式：标准 TLS 1.2，公共证书，无双向证书（实测）

`zt.yuexiu.com` 的 DNS 在当前网络（Clash）被拦，但用 AliDNS/DoH 可解析到 `210.21.123.7`
（Cloudflare 解析到 `203.198.220.122`，属不同节点）。对该地址做 TLS 握手实测：

```
subject: C=CN, ST=广东省, L=广州市, O=广州越秀企业集团股份有限公司, CN=*.yuexiu.com
issuer : C=CN, O=TrustAsia Technologies, Inc., CN=TrustAsia OV TLS RSA CA 2024
Protocol: TLSv1.2    Cipher: ECDHE-RSA-AES128-GCM-SHA256    PKEY: RSA 2048
No client certificate CA names sent          ← 服务端不请求客户端证书
No ALPN negotiated
verify return code: 0 (ok)                   ← 公共 CA 链，系统信任即可
```

结论：**不是国密、不强制双向证书、证书是公共 CA 的 `*.yuexiu.com` 通配证书**。
所以"登录/控制面"这一层用普通 TLS + 系统信任链就够，不需要额外安装根证书。

但同一个 443 **对未授权来源直接静默断开**（实测，2026-11-07）：

```

curl: (52) Empty reply from server          # TLS 握手成功，随后服务端 close_notify
# 连"什么都不发"也立即 EOF：
silent   recv 0 after 0.0 s
http-get recv 0 after 0.0 s
```

即：**不是路径/报文的问题，是来源被拒**。可能原因：公司网络/IP 白名单，或需要先发 SPA 敲门包
（引擎里有 `SPTrustSpaClient::ActiveSPAPinWithUDP`、`knock_addr`、`qianxin-spa://`）。
因此"在任意网络下用 token 直接 POST 登录"这条路在当前网络走不通，必须先满足网络/SPA 前置条件。

### 18.3.1 登录参数（补充说明）

- 登录请求由 Qt 的 `QNetworkAccessManager` 发出，走系统信任链，**没有客户端证书** → 登录这一步就是标准 TLS。
- 隧道参数（`ssl_twoway` 双向证书、`ssl_smx` 国密、`vpn_sni`）来自登录/会话应答，引擎日志为
  `Connecting to vpn[%s_%d]: ssl_sni=%s, ssl_twoway=%d, ssl_smx=%d`，关键字 `vpn_ssl_twoway` 出现在
  `TrustService` 的字符串表里 —— 即**客户端在登录前不知道**，只能登录后读应答。
- 实现上的取舍：`YX` 先按普通 TLS 连（`verify` 可配），登录后把 `vpn_host/vpn_port/vpn_sni/vpn_ssl_twoway/ssl_smx`
  原样展示出来；若 `vpn_ssl_twoway=1`，需要补证书申请流程（引擎侧有 `OnReqCertApply`），
  若 `ssl_smx>0`，需要国密 TLS 栈（rustls 不支持，需换 OpenSSL/国密库）。

## 19. 实测：网关在 TLS 之后立即拒绝（2026-11-07 现场）

在用户机器上实测（`zt.yuexiu.com` 解析到 `210.21.123.7`，另一节点 `203.198.220.122`）：

```
# 1) 什么都不发
tls TLSv1.2 ECDHE-RSA-AES128-GCM-SHA256   from 210.21.123.7:443
recv 0 after 0.0 s            ← 服务端 close_notify

# 2) 发 HTTP
$ curl -k --resolve zt.yuexiu.com:443:210.21.123.7 https://zt.yuexiu.com/api/v2/authn/login -d '{...}'
curl: (52) Empty reply from server

# 3) 发 PTUN 帧（"PTUN"+BE32(len)+{"local_subnet":""}）
sent 27 bytes → recv 0

# 4) 换另一个解析节点 203.198.220.122，行为相同
```

`YX` 里对应两条报错：
- 「获取 token 失败：网关在 TLS 握手后立即关闭」← 登录 POST 得到空应答；
- 「握手失败：网络错误：failed to fill whole buffer」← `authz` 读帧时 `read_exact` 立刻 EOF。

两条是同一个原因：**服务端在 TLS 握手完成后主动断开，与请求内容无关**（空连接也一样）。
所以既不是路径/报文问题，也不是我们 TLS 实现的问题。

### 19.1 两种可能，以及为什么现在还区分不了

| 假设 | 依据 | 区分方法 |
|---|---|---|
| **来源 IP 白名单** | 两个节点、三种首包都被断；TLS 层完全正常 | 换到官方客户端能正常用的网络再试 |
| **SPA 敲门未做** | 引擎里有 `SPSPAModule`（`SetSpaAddrKey`/`CaculateSpaKey`/`gen_spa_outdata`）、`SPTrustSpaClient::sendUDPWithItem`、`default_spa_key`、`spatemp.file`；SPA 是 **UDP** 且先于连接 | 抓到官方客户端登录时的 UDP 包即可确认 |

客户端把 SPA 信息持久化在 `<base>/spatemp.file`（`[spa][module] successfully read spainfo from spatemp.file`），
本机没有该文件（从未成功登录过），所以无法离线还原 key。

### 19.2 需要的下一步（只能在实际可用环境做）

1. 在**官方云上越秀的零信任能正常登录**的网络里复跑 `ZtView → 用登录态获取 token`：
   - 成功：`session` 里会直接给出 `vpn_host/vpn_port/vpn_sni/vpn_ssl_twoway/ssl_smx`，第 18.3 的问号补齐。
2. 若仍然被断，请在该网络抓 30 秒包（登录瞬间）：

   关键看：是否有 **UDP** 敲门包（目的端口、长度、是否随机化）、TLS 之后客户端发的第一批字节。
   有了这个 pcap，`SPA`/白名单两种假设立刻能区分。
3. 另一条更快的兜底：官方客户端在本机跑起来后，用 `lsof -nP -iTCP -sTCP:ESTABLISHED | grep 3544`

## 20. 真正的门禁：SPA 藏在 TLS ClientHello 扩展 0x00e9（2026-11-07）

### 20.1 抓包对比（`/tmp/zt.pcap`）

官方客户端的 ClientHello（652 字节，11 个扩展）：

```
0x00e9  len=325   03 34 33 64 62 38 35 65 ...     ← 私有扩展
0x0000  server_name: zt.yuexiu.com
0x000a/0x000b/0x0023/0x002b/0x0033 ...
```

`0x00e9` 的 325 字节内容与同一时刻发往 **UDP:443** 的 SPA 包**逐字节相同**：

```
len 325 | 0x03 | 43db85e636749d4368129c139207c3a8 | 00000000 | 144B 签名/密文
                ↑ 设备/用户 ID（固定）              ↑ 每次不同
```

即：**SPA 同时走 UDP 和 TLS 扩展两条路**，网关在握手里读扩展。

### 20.2 对照实验（自写 C 客户端，用 `SSL_CTX_add_custom_ext` 塞 0x00e9）

| ClientHello | 服务端反应 |
|---|---|
| 不带 0x00e9（`YX` 现行实现） | TLS 完成 → **静默 close** |
| 带 0x00e9，内容全 0 | 握手期 **`decode error` alert** |
| 带 0x00e9，内容为 10 分钟前的真实 SPA | 同样 `decode error` |

结论：扩展被网关**真正解析**；内容不合法就 alert，缺失就静默丢弃。SPA 有**很短的有效期**
（客户端每 ~30 s 重发一次，抓到的包 10 分钟后即失效）。

### 20.3 SPA 的来源（决定"能否独立"）

- `SPSPAModule::LoadBuildInSpaInfo` 从键值库里读 `"default_spa_key"`，再 `SPSpaInfo::FromJSON`；
- 键值库是 `moddata.db`（`GenDefaultDBPath`/`GetCurrentDBPath`），本机不存在；
- 另有 `spatemp.file` 缓存（`[spa][module] successfully read spainfo from spatemp.file`），本机也没有；
- 结构里带 `aes_key` / `hmac_key` / `profile`，由服务端在登录流程中下发。

因此 **无法离线生成合法 SPA**：不登录拿不到 key，不拿 key 又过不了握手（先有鸡还是先有蛋）。
唯一可行的验证是"在有效期内重放"——需要一份新鲜抓包。

### 20.4 本地代理也不能直接借用

`trustagentservice` 在 `36440–36443` 提供 `/_trustproxy/ping`（返回 pong）和 `/proxyserver/check`；
用 CONNECT 访问会被要求代理认证：

```
无凭据           → 407 Proxy-Authenticate: Basic realm="Access to the internal site"
带 trustagent:xxx → 401（口令被拒）
```

口令算法（第 12 节：`HOTP(user)`）算出来的值不被接受，说明这层还叠加了会话/设备因子。
另外官方客户端实际是靠 **utun**（`trustvnic` 正在运行）接管流量，不依赖这个代理端口。

### 20.5 结论

- 协议层（帧、authz、登录、TLS 参数）已经逆向清楚并实现；
- 卡点收敛为**一个**：SPA 的 `aes_key/hmac_key` 只能由服务端下发；
- 想继续，只有三条：① 抓到有效期内的 SPA 并验证重放；② 厂商提供 SPA key / SDK；③ 继续复用官方客户端。

### 20.6 重放实验（决定性，2026-11-07 11:00）

抓包权限修好后，用**抓包后 <1 秒**的新鲜 SPA 做重放（`spa_cli` 把最新一包塞进 0x00e9 扩展）：

```
spa: 11:00:46.424753 ... -> /tmp/spa_live.bin 325 bytes
spa payload: 325 bytes, head=03343364
TLS failed: error:0A00041A:SSL routines::tlsv1 alert decode error
```

同一时刻，官方客户端用同样的包可以正常握手（它的连接一直活着）。也就是说：

- **不是"包过期"**（<1 秒）；
- **不是"格式不对"**（字节完全一致，且服务端确实解析了扩展）；
- 只能是 **SPA 与客户端身份/会话绑定 + 抗重放**（签名里含有服务端认可的一次性信息，
  或被网关记录为已使用）。

### 20.7 最终结论（独立实现的边界）

| 层 | 状态 |
|---|---|
| TLS（SNI/套件/证书/无 mTLS） | ✅ 已确认并可复刻（第 18.3 节） |
| 帧格式 `tag/plen/dlen` + 对齐 | ✅ 已实现并有单测（第 14 节） |
| `authz` JSON-RPC（`0x11000001`） | ✅ 已实现并有单测 |
| `trust_session_login`（`auth_factor=99` + 越秀 token） | ✅ 已实现并有单测 |
| 登录/TCP 路径 | ✅ 已确认 |
| **SPA（TLS 扩展 `0x00e9`）** | ❌ **无法生成、无法重放**：key 由服务端下发（`moddata.db` 的 `default_spa_key`），且抗重放 |

结论：**在拿不到厂商 SPA key / SDK 的前提下，无法做出一个能真正接入网关的独立客户端**。
这不是工作量问题，是密码学门禁：网关只接受用它下发密钥签出的、一次性的 SPA。

可行的现实选择（按代价排序）：

1. **继续用官方客户端**：它在跑时用 utun 接管系统流量，`YX` 直接 `upstream=direct` 就能访问内网，
   不需要填任何地址/token（已实测：默认路由与内网 /32 都指向 utun）。
2. **向 IT/厂商要 SPA 预共享密钥**（或要 `default_spa_key` 的发放接口）：拿到即可复用本仓库
   已实现的 `zt_tunnel`（帧/authz/登录都是现成的）。
3. 厂商 SDK（第 11 节 Android 的 `libzerotrust.so` 形态）——最省事，但需要商务配合。

### 21.6 ✅ 找到官方客户端的免认证本地代理（关键）

登录后读系统代理就真相大白：

```
$ scutil --proxy
ProxyAutoConfigEnable   : 1
ProxyAutoConfigURLString: http://127.0.0.1:54753/get_trust_pac?proxy_server=127.0.0.1:50598
```

- `54753` 是 **PAC 服务**（我们之前误当成代理口，所以一直 407/401）；
- `http://127.0.0.1:50598` 才是真正的**转发代理**。

实测（无任何凭据）：

```
CONNECT pan.bingolink.biz:443            → 200
CONNECT ywblj.yuexiu-finance.com:443     → 200
CONNECT www.baidu.com:443                → 200

curl -x http://127.0.0.1:50598 https://ywblj.yuexiu-finance.com/  → 302
curl -x http://127.0.0.1:50598 https://pan.bingolink.biz/        → 200
```

即：**官方客户端本来就开着一个免认证的 HTTP 代理**（端口动态），并且通过系统 PAC 公布出来。
`YX` 的 `upstream=auto` 正是读 `ProxyAutoConfigURLString` 里的 `proxy_server=`，所以现在能自动命中。

这解决了"怎么用零信任"；剩下的是"怎么不影响 Clash"——下一步验证杀掉 `trustvnic`（utun 消失）
后这个代理是否仍然可用。

### 21.7 ✅ 最终可用形态：零信任只做本地代理，Clash 保留默认路由（2026-11-07 实测）

**第一次尝试**（直接 `killall trustvnic`）失败：utun 消失、Clash 恢复，但引擎把隧道也拆了，
本地代理口不再监听，SDK 的 `status` 仍谎报 `online`。→ **trustvnic 是命脉，不能杀**。

**第二次尝试**（保留 trustvnic，只删它抢走的默认路由）成功：

```bash
# 登录后 ZT 会把 default 指向自己的 utun
$ netstat -rn -f inet | grep default
default  192.168.5.1   UGScg   en0
default  198.168.1.23  UGScIg  utun8      ← ZT 抢走的

sudo route delete default -ifscope utun8
```

删除后实测（重启客户端再登录一次，PAC 端口从 50598 变为 65312）：

```
$ scutil --proxy
ProxyAutoConfigURLString : http://127.0.0.1:54753/get_trust_pac?proxy_server=127.0.0.1:65312

$ netstat -rn -f inet | grep -E "^default|^0/1|^128"
default    192.168.5.1  UGScg  en0          ← Clash 拿回默认路由
128.0/1    198.18.0.1   UGSc   utun1024     ← Clash TUN

$ curl -x http://127.0.0.1:65312 https://ywblj.yuexiu-finance.com/   → 302   （内网，走 ZT）
$ curl -x http://127.0.0.1:65312 https://www.baidu.com/              → 200   （代理可用）
$ curl https://www.baidu.com/                                        → 200   （直连/Clash 正常）
$ netstat -rn -f inet | grep -c utun8                                → 181   （内网 /32 仍在 ZT）
```

**结论：可以共存。** 零信任只承担"内网 /32 路由 + 本地代理"，公网默认路由还给 Clash。

`YX` 侧不需要任何硬编码：`upstream=auto` 读系统 PAC 的 `proxy_server`，
实测输出 `system proxy => Some(("127.0.0.1", 65312, "system-proxy"))`（`live_system_proxy` 测试）。

注意点：
1. 代理端口每次登录都会变（50598 → 65312），所以必须靠 PAC 发现，不能写死；`auto` 缓存 30 s。
2. 重新登录后 ZT 可能再次抢默认路由，需要重复一次 `route delete`；可后续做成开机/登录后的守护。
3. DNS 系统扩展仍在运行；当前 `scutil --dns` 显示解析仍走 en0，暂未见冲突，后续再评估是否停用。

### 21.8 切换零信任后的"短暂失灵"：几层缓存叠加（2026-11-07）

注销零信任后立刻访问会出现一段"Clash 好像坏了"的窗口，实测原因有四层，按影响从大到小：

| 层 | 现象 | 数据 |
|---|---|---|
| 1. `YX` 上游发现缓存 | 本地代理端口每次登录都会变（50598→65312→…），缓存 30 s 内仍指向旧端口，请求直接失败 | 已修复：`zt_sdk_login/logout` 成功后调用 `reset_upstream_cache()` |
| 2. Clash 的 DNS 上游 | 解析不到的域名会等上游超时才回 SERVFAIL | `dig ywblj.yuexiu-finance.com` → **Query time: 5000 msec / SERVFAIL**（正常的公网域名 0.02 s） |
| 3. 系统 DNS 缓存 | 注销后内网域名的 mock IP / 否定结果仍在 mDNSResponder 里 | 需要 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` |
| 4. Clash 重建路由/DNS | utun 消失是接口事件，Clash 需要几秒重挂 split 路由与 `dns-hijack` | 期间 `default` 可能短暂指向 en0 而 0/1、128/1 缺失 |

补充：`/etc/hosts` 里那 50 条 `10.164.40.101 …yuexiu.com`（标注 `#金融云`，11-03 修改）
**不是零信任写的**，是人工/公司工具加的；登录 ZT 时它们走 utun 的 10/8 路由，注销后没有路由，
访问就会挂到超时——这也是"注销后感觉网络坏了"的一个来源。

排查顺序建议：先 `curl https://www.google.com`（验证 Clash），再 `dig <内网域名>`（看是不是 5 s 超时），
最后看 `YX` 日志里的上游端口是否等于 `scutil --proxy` 里的 `proxy_server`。

## 23. 官方客户端的按需启动（2026-11-07）

目标：平时不让 TrustAgent 常驻内存，只在 `YX` 需要零信任时拉起，注销即释放。

### 23.1 launchd 组成

| 项 | 位置 | 是否驻留 | 处理 |
|---|---|---|---|
| `trustagentsdk`（JSON-RPC 登录入口） | `/Library/LaunchAgents/com.legendsec.trustagentsdk.plist` | `RunAtLoad` + `KeepAlive` | 改成按需，保留 plist |
| `trustagentservice`（本地服务/引擎配套） | `~/Library/LaunchAgents/com.legendsec.trustagentservice.plist` | 同上 | 改成按需，保留 plist |
| `trustdservice`（设备合规采集，root） | `/Library/LaunchDaemons/com.legendsec.trustdservice.plist` | 同上 | 可改按需；关掉不影响登录即可删 |
| `jobblesshelper` | `/Library/LaunchDaemons/…` | `MachServices`，用时才起 | 保留 |
| `trustuninstall` | `/Library/LaunchDaemons/…` | `WatchPaths`，删 App 时触发 | 可删，不影响功能 |

注意：DNS 劫持来自系统扩展 `com.legendsec.trustagentlauncher.dnsproxy`，不在这几个 plist 里。

### 23.2 关键实测：`kickstart` 会被客户端踢掉

把 `RunAtLoad`/`KeepAlive` 设为 `false` 后：

- `launchctl bootstrap gui/501 …trustagentsdk.plist` 返回 0，任务可见；
- 但 `launchctl kickstart -k gui/501/trustagentsdk` 返回 0 后，任务很快又从 `gui/501` 消失，
  进程起不来，35440-35443 全部 closed；
- 直接执行二进制 `/Applications/TrustAgentLauncher.app/Contents/MacOS/trustagentsdk` 则正常：
  四个端口立刻监听，`status` 返回 `offline`。

结论：**launchd 只适合做"入口"，不能作为可靠拉起手段**（客户端会 bootout 它不认的 job）。
可靠的按需拉起顺序是：`open -a TrustAgentLauncher.app` → `launchctl kickstart` → 进程仍不在就
`Command::spawn` 直接跑二进制。

### 23.3 实现

`src-tauri/src/zt_sdk.rs`：

- `agent_start()`：先 `open -a`（客户端没跑时），再对 `trustagentservice` / `trustagentsdk`
  逐个 `kickstart`，1.5 秒内没起来就 `spawn_bin()` 兜底（stdout/stderr 接 /dev/null，不阻塞）。
- `ensure_sdk()`：先探测 35440-35443，端口开但不回包视为卡死（`restart_sdk_daemon()` 杀掉），
  然后统一走 `agent_start()`，最多等 10 秒。
- `agent_stop()`：先 `launchctl kill`，再按进程名 `pkill` SDK、service、Launcher、TrustAgent；
  1.5 秒后检查 SDK 是否被 launchd 复活，若复活就提示"请先关闭 KeepAlive"。
- `zt_sdk_logout` 成功后再调 `agent_stop()`，返回"相关进程已退出"或上面的提示。

### 23.4 客户端会改写 plist（实测）

- `trustagentsdk.plist` 在 `/Library/LaunchAgents`（root 所有）：改成 `false` 后**能保持**。
- `trustagentservice.plist`（`~/Library/LaunchAgents`）与 `trustdservice.plist`（`/Library/LaunchDaemons`）：
  客户端每次启动都会改回 `RunAtLoad`/`KeepAlive=true`，手工改的值会被还原。
- 因此按需启动只依赖两件事：
  1. SDK 的 plist 一次性改 `false`（登录入口不常驻）；
  2. `YX` 注销时 `launchctl bootout gui/$UID/{trustagentsdk,trustagentservice}`——
     bootout 会卸载任务、解除 KeepAlive 守护，即使 plist 是 `true` 也不会被自动拉起。
- 实测注销后只剩 `trustdservice`（root，约 25 MB）。它无法在应用内停掉，需要
  `sudo launchctl bootout system/com.legendsec.trustdservice`（重启后会回来，因为 plist 被改回 true）。
- 关掉 `trustdservice` 后若登录报设备/合规类错误，说明网关依赖设备态检查，保持它运行即可。
- DNS 劫持的系统扩展（`com.legendsec.trustagentlauncher.dnsproxy`）由客户端拉起，不受 plist 控制。

### 23.5 完整循环实测

```text
left after stop:  ["trustdservice"]
ensure_sdk ok:    port=35443
left after start: ["trustagentsdk", "trustagentservice", "TrustAgentLauncher", "trustdservice"]
```

即：注销后用户级进程全部退出，再次登录能自动拉起并监听 35440-35443。
